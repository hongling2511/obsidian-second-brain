🥷## 第一课：区块链开发者真正操作的对象——状态

### 1. 先问：一笔交易到底是什么？

用户点击“转账”时，钱包并没有直接修改区块链余额。

它做的是：

1. 组织一条请求：谁要做什么、给谁、多少、支付多少 Gas
2. 用私钥签名
3. 把签名后的交易广播给节点
4. 节点验证后，执行这条交易
5. 执行结果改变链上的状态

所以：

> **交易是“请求改变状态的指令”，不是状态本身。**

可以把以太坊抽象成一个状态转换函数：

$$
S_{t+1} = F(S_t, T)
$$

- $S_t$：当前链上状态
- $T$：交易
- $F$：执行规则
- $S_{t+1}$：交易执行后的新状态

例如：

```text
原状态：
Alice = 10 ETH
Bob   = 2 ETH

交易：
Alice 给 Bob 转 3 ETH

新状态：
Alice = 7 ETH
Bob   = 5 ETH
```

### 2. 钱包、执行客户端、共识客户端分别做什么？

```text
钱包
  └─ 创建交易 + 私钥签名

执行客户端
  └─ 验证交易 + 执行 EVM + 计算状态变化

共识客户端
  └─ 参与区块提议、投票、分叉选择、最终性

区块浏览器
  └─ 读取链上数据并展示给人看
```

最容易混淆的一点：

> **执行客户端决定“这笔交易执行后状态变成什么”；共识客户端决定“哪个区块被网络接受为链的一部分”。**

两者不是竞争关系，而是分工关系。

## 一笔以太坊交易的旅程

```text
1. 钱包创建交易
       ↓
2. 私钥签名
       ↓
3. 广播到节点的 mempool
       ↓
4. 执行客户端验证并执行
       ↓
5. 验证者把交易放进区块
       ↓
6. 其他节点重新执行验证
       ↓
7. 共识机制接受该区块
       ↓
8. 状态更新
```

### 关键区分

**Mempool 不是区块链。**

交易进入 mempool，只表示：

> 某个节点暂时认为这笔交易有效，并准备传播或打包。

它还可能：

- 被替换
- 被丢弃
- 因 Gas 太低而长期等待
- 因 nonce 冲突而无法执行
- 根本没有进入最终区块

只有交易进入被网络接受的区块，才成为链状态的一部分。

### 为什么其他节点要“重新执行”？

因为区块生产者可能撒谎。

如果提议者声称：

```text
Alice 给 Bob 转了 100 ETH
```

其他节点不能只相信它，而要使用相同的规则重新计算：

```text
旧状态 + 这笔交易 = 新状态？
```

如果计算结果不一致，区块就会被拒绝。

这就是区块链开发中的核心思想：

> **共识不是相信某个节点，而是让节点独立运行同一套确定性规则，检查是否得到同一个结果。**

## Nonce 为什么存在？

假设 Alice 发出两笔交易：

```text
交易 A：给 Bob 转 1 ETH
交易 B：给 Bob 转 2 ETH
```

如果网络先收到 B，再收到 A，节点需要知道它们的顺序。

因此 Alice 的交易带有递增的 nonce：

```text
交易 A：nonce = 7
交易 B：nonce = 8
```

Nonce 同时解决两个问题：

1. **排序**：确定同一账户交易的执行顺序
2. **防重放**：同一笔签名交易不能被无限重复执行

可以把它理解为账户发出的“序号”。

```text
nonce = 7 的交易执行成功
→ 下一笔通常必须是 nonce = 8
```

这也是为什么一笔低 nonce、卡住的交易，可能阻塞同一账户后面的交易。

🥷## 第三课：EVM 与 Gas

上一节已经知道：交易最终要由执行客户端计算状态变化。

现在的问题是：

> 如果每个节点都要重新执行合约，谁来保证执行不会无限循环、拖垮所有节点？

答案是两个设计：

1. **EVM**：所有节点运行同一种确定性虚拟机
2. **Gas**：每一步计算都有成本

---

## 1. EVM 是什么？

EVM 可以理解为：

> **一台所有以太坊节点都能复现的确定性虚拟机。**

同一笔交易、同一个旧状态、同一套 EVM 规则，必须得到同一个结果：

$$
F(S, T) = S'
$$

不能出现：

```text
节点 A：余额变成 7 ETH
节点 B：余额变成 8 ETH
```

否则网络无法形成共同账本。

所以智能合约不能依赖：

- 当前机器时间
- 随机数生成器
- 外部网络请求
- 节点本地文件
- 不同节点可能不同的环境

---

## 2. Gas 为什么存在？

假设有人部署：

```solidity
while (true) {
    // 永远循环
}
```

如果执行免费，所有节点都可能永远卡住。

因此每条 EVM 指令都有 Gas 成本：

```text
读取存储：消耗 Gas
写入存储：消耗 Gas
哈希计算：消耗 Gas
调用其他合约：消耗 Gas
```

交易会设置一个 Gas limit：

```text
Gas limit = 允许这笔交易最多消耗多少 Gas
```

如果执行过程中 Gas 用完：

- 交易执行失败
- 状态变化通常回滚
- 已消耗的 Gas 不退还
- 区块本身仍可能包含这笔失败交易

Gas 的本质是：

> **把全网共享的计算资源变成有上限、有价格的资源。**

---

## 3. Gas 费用的基本公式

传统表达可以写成：

$$
\text{交易费} = \text{实际消耗 Gas} \times \text{Gas Price}
$$

现代以太坊的费用进一步拆成：

$$
\text{Gas Price} = \text{Base Fee} + \text{Priority Fee}
$$

- **Base Fee**：由网络拥堵程度决定，并被销毁
- **Priority Fee**：给验证者的小费，用来提高打包意愿

注意：

```text
Gas limit ≠ 实际费用
```

Gas limit 是“最多允许消耗多少”；实际费用取决于交易真正执行了多少指令。

---

## 4. 一个重要后果

写入链上存储通常比读取昂贵，因为：

```text
读取：节点临时计算即可
写入：所有节点都要长期保存并复制
```

所以智能合约开发者会关心：

- 减少不必要的 storage 写入
- 避免重复计算
- 限制循环规模
- 防止外部调用带来的不可控 Gas
- 设计清晰的失败和回滚逻辑

这也是“区块链程序”和普通后端程序的根本差异：

> 普通程序主要优化一台服务器；智能合约要优化所有节点共同重复执行的成本。

现在检查核心概念：


> [!question] Quiz
> 为什么智能合约执行需要消耗 Gas？
>
> 1. 保证交易一定会成功执行
> 2. 让区块浏览器能够显示合约源码
> 3. 限制计算资源滥用，避免无限循环拖垮节点
> 4. 让钱包能够生成私钥


> [!success] Quiz — correct ✓
> Your answer: 3. 限制计算资源滥用，避免无限循环拖垮节点
> Correct answer: 3
>
> Gas 为计算和存储设定成本与上限，防止攻击者用无限循环或高成本操作耗尽所有节点资源。Gas 并不保证交易成功；交易也可能因耗尽 Gas 或其他原因失败。

再补上一个容易误解的点：**交易失败不等于没有发生任何链上记录。**

例如合约执行时：

```solidity
require(balance >= amount, "insufficient balance");
```

如果余额不足：

1. 交易仍可能被打包进区块
2. 节点执行到 `require`
3. 状态变化回滚
4. 交易标记为失败
5. 已消耗的 Gas 仍然支付
6. 区块链上会留下这笔失败交易的记录

因此：

```text
交易被收录 ≠ 交易执行成功
```

开发者需要分别查看：

- 交易是否上链
- `status` 是否成功
- `revert reason`
- 实际 Gas 使用量
- 事件日志是否产生

核心心智模型：

```text
交易记录：发生过一次执行尝试
状态变化：这次尝试是否成功改变了状态
```

这两个概念必须分开。

🥷## 第四课：合约数据到底存在哪里？

Solidity 里最重要的成本区别之一，是数据位置。

### 1. `storage`：永久链上状态

```solidity
uint256 public totalSupply;
mapping(address => uint256) public balances;
```

这些变量属于合约状态，会被写入链上。

特点：

- 交易结束后仍然存在
- 所有节点都要保存
- 写入通常昂贵
- 修改它会改变合约状态

可以把 `storage` 看成数据库。

---

### 2. `memory`：本次执行的临时内存

```solidity
function sum(uint256 a, uint256 b)
    external
    pure
    returns (uint256)
{
    uint256 result = a + b;
    return result;
}
```

`result` 只在本次调用期间存在。

特点：

- 执行结束后消失
- 不会永久写入链上
- 通常比 storage 便宜
- 适合临时计算

可以把 `memory` 看成函数运行时的内存。

---

### 3. `calldata`：交易带来的只读输入

```solidity
function greet(string calldata name)
    external
    pure
    returns (string memory)
{
    return name;
}
```

`name` 来自调用者发送的交易数据。

特点：

- 属于本次调用的输入
- 只读
- 执行结束后不成为合约状态
- 外部函数常用它接收参数

---

## 一张表

| 位置 | 是否持久化 | 是否可修改 | 类比 |
|---|---:|---:|---|
| `storage` | 是 | 是 | 数据库 |
| `memory` | 否 | 是 | 临时内存 |
| `calldata` | 否 | 否 | 请求参数 |

这三者的区别，本质上仍然来自上一课：

> **只有写入状态的操作，才会改变链上世界；临时数据只服务于本次执行。**

例如：

```solidity
function transfer(address to, uint256 amount) external {
    balances[msg.sender] -= amount; // 修改 storage
    balances[to] += amount;         // 修改 storage
}
```

这里真正改变链上状态的是 `balances`，而不是函数参数 `to` 和 `amount`。

---

## 为什么开发者必须关心？

因为错误的数据位置会导致：

- Gas 浪费
- 数据修改不了
- 以为保存了数据，实际执行完就消失
- 合约逻辑产生严重漏洞

先做一个关键判断：


> [!question] Quiz
> 如果合约需要在今天的交易结束后，仍然记住某个用户的余额，这个余额应该放在哪里？
>
> 1. calldata
> 2. storage
> 3. memory
> 4. stack-only


> [!success] Quiz — correct ✓
> Your answer: 2. storage
> Correct answer: 2
>
> 只有 storage 是持久化的合约状态，会在交易执行结束后保留下来，并由所有节点共同维护。memory、calldata 和栈数据都只服务于当前执行。


> [!abstract] PI

再补一个经常被误用的概念：**事件日志不是合约状态。**

```solidity
event Transfer(address indexed from, address indexed to, uint256 amount);
```

执行：

```solidity
emit Transfer(msg.sender, to, amount);
```

事件的作用是：

- 给前端和区块浏览器读取
- 记录“发生过什么”
- 方便索引和查询

但事件不能替代：

```solidity
balances[user]
```

因为合约代码不能像读取 storage 那样，把历史事件当作当前状态使用。

所以：

```text
storage = 合约未来执行时可以读取的状态
event   = 给链下应用查询的历史日志
```

例如转账函数通常需要两者：

```solidity
balances[from] -= amount;
balances[to] += amount;
emit Transfer(from, to, amount);
```

- 前两行改变真实余额
- 最后一行通知前端发生了转账

检查这一点：


> [!question] Quiz
> 为什么 ERC-20 转账通常既要修改 `balances`，又要 `emit Transfer`？
>
> 1. 修改 balances 会自动产生所有标准事件
> 2. 两者作用完全相同，只是写法不同
> 3. 余额供合约读取，事件供链下应用索引和展示
> 4. 事件保存余额，balances 只用于前端展示


> [!success] Quiz — correct ✓
> Your answer: 3. 余额供合约读取，事件供链下应用索引和展示
> Correct answer: 3
>
> balances 是合约可读取的持久化状态；Transfer 事件是链下应用、钱包和浏览器读取转账历史的重要接口。修改状态不会自动替代事件。


> [!abstract] PI

本节掌握了 Solidity 数据的三种位置：

- `storage`：持久化链上状态
- `memory`：本次执行的临时数据
- `calldata`：只读的调用输入
- `event`：供链下应用索引的日志，不是合约状态

核心区别：

```text
合约未来要读取 → storage
本次计算暂时用 → memory
外部调用传进来 → calldata
通知前端发生了什么 → event
```
