### 第一步：统一的对象是什么？

如果三端都强行做到视觉一致，会出现问题：

- 桌面端失去键盘快捷键、右键、拖放等效率能力
- 移动端控件太小、层级太深，不适合触控
- Web 端可能破坏浏览器的返回、链接和分享习惯

所以设计系统真正应该统一的是：

- **品牌语义**：产品是什么、传达什么气质
- **内容层级**：什么最重要、什么次要
- **核心任务**：用户要完成什么
- **状态模型**：加载、成功、失败、空状态、禁用等
- **交互意图**：创建、编辑、删除、确认、撤销
- **质量底线**：可访问性、反馈、错误恢复

而以下内容可以平台化：

- 导航形态
- 布局结构
- 控件样式
- 输入方式
- 手势、快捷键、右键菜单
- 弹层和系统反馈方式

可以把它压缩成一句话：

> **跨平台统一“用户要完成什么”，平台化表达“用户怎么完成它”。**

这就是后面所有规范的根。

```mermaid

  B --> C[平台表达]
  C --> D[具体界面]
```

### 第二步：为什么不能只写“组件规范”？

很多团队一开始就定义：

- 按钮圆角是多少
- 主色是什么
- 卡片间距是多少
- 输入框长什么样

- 数据加载中怎么办？
- 没有数据怎么办？
- 请求失败怎么办？
- 用户没有权限怎么办？
- 用户正在编辑时网络断了怎么办？

因此设计系统不能只是“组件外观库”，还必须描述：

> **组件在不同状态下如何工作。**

```text

```

> **规范状态和行为，比规范静态外观更重要。**

### 第三步：为什么要使用语义令牌？

如果直接写：

```text
蓝色 = #2563EB
```

组件就被绑死在某个具体颜色上。换主题、做深色模式或提高对比度时，会很难维护。

更好的方式是：

```text
color.action.primary
color.surface.default
color.text.muted
color.feedback.error
```

组件只关心“这个颜色承担什么职责”，不关心它具体是蓝色、绿色还是其他颜色。

因此：

> **设计令牌应该描述语义，而不是描述原始值。**

关系可以理解为：

```text
语义令牌 → 主题映射 → 平台组件
```

例如：

```text
color.action.primary
       ↓
浅色主题：深蓝
深色主题：亮蓝
高对比主题：高对比蓝
```

### 第四步：平台差异不是“实现细节”

同一个任务，在不同平台上有不同的输入能力和使用情境。

以“选择一个文件”为例：

- **Web**：文件选择器、拖放、可分享链接
- **移动端**：系统文件选择器、相册、相机、触控
- **桌面端**：文件选择器、拖放、路径输入、快捷键

如果只追求界面一致，就会浪费平台本来提供的能力。

可以把平台差异分成四类：

| 维度 | Web | 移动端 | 桌面端 |
|---|---|---|---|
| 输入 | 鼠标、键盘、触控 | 触控、传感器 | 鼠标、键盘、拖放 |
| 空间 | 浏览器窗口 | 小屏、单手 | 大屏、多窗口 |
| 导航 | URL、浏览器返回 | 系统返回、底部导航 | 侧栏、菜单、窗口 |
| 工作方式 | 页面/链接 | 短时、碎片化 | 长时、高密度 |

所以我们需要区分：

- **响应式**：同一平台内，布局适应窗口尺寸
- **自适应**：根据平台能力和使用情境改变交互方式

例如：

```text
窗口变窄 → 响应式：三列变一列
从桌面切到移动端 → 自适应：侧栏变底部导航
```

这条原则是：

> **尺寸变化用响应式解决，能力和情境变化用自适应解决。**

### 第五步：组件应该从哪里开始？

不要先把所有组件都做一遍。更好的顺序是：

1. 找出产品最高频、最关键的任务
2. 找出这些任务反复出现的交互
3. 抽象组件和模式
4. 在三端验证
5. 再决定是否沉淀为通用规范

例如一个任务型产品，优先级可能是：

```text
登录 → 搜索 → 创建 → 编辑 → 保存 → 删除 → 错误恢复
```

对应的组件和模式可能是：

- 表单
- 搜索框
- 筛选器
- 编辑器
- 保存反馈
- 确认流程
- 错误提示
- 空状态

这比一开始制作几十个视觉组件更可靠，因为它们来自真实任务，而不是抽象猜测。

核心原则：

> **先抽象任务模式，再抽象视觉组件。**

## 表单校验：统一规则，适配反馈方式

先区分两件事：

- **校验规则**：三端应尽量一致
- **错误呈现**：可以根据平台调整

例如“标题必填”：

```text
共享规则：标题不能为空
Web：字段下方显示错误文本
移动端：滚动到错误字段并聚焦
桌面端：字段错误 + 快捷键导航
```

### 校验的三个时机

1. **输入时**：尽早发现明显错误，但不要打扰用户
2. **离开字段时**：检查当前字段是否完整
3. **提交时**：检查整个表单，不能只依赖前端校验

### 错误信息应包含三部分

```text
发生了什么
为什么不对
如何修复
```

差的提示：

```text
输入无效
```

好的提示：

```text
标题不能为空，请输入记录名称
```

错误设计还要满足：

- 错误靠近对应字段
- 不只用颜色表达
- 保留用户已经输入的内容
- 多个错误时提供整体概览
- 错误消失后，状态要明确更新

关键原则：

> **统一“什么算错误”和“如何修复”，平台化“错误如何被用户看到”。**

## 创建过程中的状态设计

“点击创建”不是一个瞬间，而是一段状态变化：

```text
可提交
→ 提交中
→ 创建成功
或
→ 创建失败
```

### 提交中

必须避免：

- 用户重复点击
- 用户误以为没有反应
- 当前输入被清空

可以表现为：

- 主按钮进入加载状态
- 暂时阻止重复提交
- 保留表单内容
- 显示“正在创建…”

### 成功后

成功反馈需要回答：

1. 创建成功了吗？
2. 创建的记录在哪里？
3. 接下来可以做什么？

例如：

```text
记录已创建
[查看记录] [继续创建]
```

### 失败后

失败反馈需要回答：

1. 失败原因是什么？
2. 内容还在吗？
3. 如何恢复？

例如：

```text
保存失败，可能是网络连接中断
内容已保留
[重试]
```

三端可有不同表达：

- Web：页面内提示或通知条
- 移动端：底部提示或页面状态
- 桌面端：状态栏、内联错误、快捷键重试

但状态语义必须一致。

```text

```

这就是“状态完整性”在真实任务中的体现。

## 三端页面结构

### Web：页面优先，兼顾分享与返回

```text
┌────────────────────────────────────┐
│ 返回   创建记录                     │
├──────────────────┬─────────────────┤
│                  │                 │
│   表单编辑区      │   预览 / 帮助区   │
│                  │                 │
├──────────────────┴─────────────────┤
│                取消      创建        │
└────────────────────────────────────┘
```

特点：

- 表单可以直接通过 URL 进入
- 使用浏览器返回时要保护未保存内容
- 宽屏时可以同时显示表单和预览
- 主要操作保持明确，但不必固定在屏幕底部

### 移动端：单手操作优先

```text
┌─────────────────┐
│ ‹   创建记录     │
├─────────────────┤
│                 │
│    表单字段      │
│                 │
│                 │
├─────────────────┤
│       创建       │
└─────────────────┘
```

特点：

- 单列布局
- 字段分组或分步
- 主操作靠近拇指可达区域
- 键盘出现时，当前输入必须可见
- 离开页面时处理草稿和未保存提醒

### 桌面端：持续工作效率优先

```text
┌────────┬──────────────────┬────────┐
│ 字段目录 │    编辑区域       │ 预览区  │
│          │                  │        │
│          │                  │        │
└────────┴──────────────────┴────────┘
```

特点：

- 支持多栏和高信息密度
- 支持键盘移动、快捷键和拖放
- 保存状态可以持续显示
- 适合长时间编辑和反复修改

### 三端的共同底线

无论布局怎么变化，都不能丢失：

- 当前编辑对象的明确标题
- 必填字段提示
- 错误定位
- 保存状态
- 取消或返回路径
- 成功后的下一步
- 未保存内容保护

所以响应式设计不是：

> 把同一个页面压缩成三种尺寸

而是：

> 在不同空间中，重新安排任务优先级。

## 可访问性：跨平台的共同底线

可访问性不是某个平台的附加功能，而是共享设计契约的一部分。

“创建记录”至少要保证：

### 视觉

- 不只用颜色表示错误
- 文本与背景有足够对比
- 焦点状态清晰
- 信息层级明确

### 输入

- Web 支持键盘操作
- 移动端控件适合触控
- 桌面端支持快捷键和精确操作
- 所有操作都有可见反馈

### 认知

- 字段标签清楚
- 错误信息说明如何修复
- 不让用户依赖记忆完成流程
- 离开、取消、删除等危险操作有明确后果

### 辅助技术

- 字段与标签正确关联
- 状态变化能被读屏感知
- 错误可以定位
- 加载状态不会让用户误以为界面失灵

核心原则：

> **同一个任务，不论用户通过视觉、键盘、触控还是辅助技术完成，都应该拥有可理解、可恢复的路径。**

## “创建记录”跨平台设计规范 v0.1

### 1. 任务目标

用户可以填写信息、保存草稿、提交创建，并在失败时恢复。

### 2. 页面组成

| 区域 | 作用 | 是否跨平台保留 |
|---|---|---|
| 页面标题 | 说明正在创建什么 | 必须 |
| 表单区 | 输入记录信息 | 必须 |
| 状态区 | 显示保存、错误、成功状态 | 必须 |
| 主操作 | 创建或保存 | 必须 |
| 辅助区 | 预览、帮助、字段目录 | 可平台化 |
| 取消 / 返回 | 离开当前流程 | 必须 |

### 3. 状态矩阵

| 状态 | 用户看到什么 | 用户可以做什么 |
|---|---|---|
| 初始 | 空表单、字段提示 | 开始填写 |
| 编辑中 | 已输入内容、草稿状态 | 修改、离开、保存 |
| 校验失败 | 字段错误、整体概览 | 修复、重新提交 |
| 保存中 | 加载状态 | 等待或取消 |
| 保存成功 | 成功反馈、记录入口 | 查看、继续创建 |
| 保存失败 | 原因、内容保留 | 重试、继续编辑 |
| 离线 | 网络状态提示 | 本地编辑或稍后重试 |

### 4. 组件清单

最小版本不需要几十个组件，只需要：

- `PageHeader`
- `FormField`
- `FieldError`
- `FormSummary`
- `SaveStatus`
- `PrimaryAction`
- `DraftRecovery`
- `SuccessFeedback`
- `RetryFeedback`
- `UnsavedChangesGuard`

### 5. 平台差异表

| 能力 | Web | 移动端 | 桌面端 |
|---|---|---|---|
| 主布局 | 单页或双栏 | 单列或分步 | 多栏 |
| 保存 | 页面内状态 | 底部操作区 | 持续保存 / 快捷键 |
| 返回 | 浏览器返回 | 系统返回 | 窗口关闭 / 快捷键 |
| 错误 | 字段旁 + 汇总 | 自动滚动定位 | 字段错误 + 快捷键导航 |
| 辅助功能 | URL、链接 | 相机、通知、离线 | 拖放、多窗口 |

### 6. 验收标准

这个任务只有在以下条件都满足时才算完成：

- 用户始终知道自己在创建什么
- 用户知道哪些字段有问题以及如何修复
- 提交过程中不会重复创建
- 失败后输入内容不会丢失
- 成功后用户能找到新记录
- 三端共享同一套任务语义
- 每个平台都使用适合自己的输入和布局方式
- 键盘、触控和辅助技术都能完成任务

最后一条原则：

> **设计规范不是规定“页面长什么样”，而是规定“任务必须可靠地完成”。**
