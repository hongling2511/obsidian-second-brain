### 第一步：统一的对象是什么？

如果三端都强行做到视觉一致，会出现问题：

- 桌面端失去键盘快捷键、右键、拖放等效率能力
- 移动端控件太小、层级太深，不适合触控
- Web 端可能破坏浏览器的返回、链接和分享习惯

所以设计系统真正应该统一的是：

- **品牌语义**：产品是什么、传达什么气质
- **内容层级**：什么最重要、什么次要
- **核心任务**：用户要完成什么
- **状态模型**：加载、成功、失败、空状态、禁用等
- **交互意图**：创建、编辑、删除、确认、撤销
- **质量底线**：可访问性、反馈、错误恢复

而以下内容可以平台化：

- 导航形态
- 布局结构
- 控件样式
- 输入方式
- 手势、快捷键、右键菜单
- 弹层和系统反馈方式

可以把它压缩成一句话：

> **跨平台统一“用户要完成什么”，平台化表达“用户怎么完成它”。**

这就是后面所有规范的根。

```mermaid
graph TD
  A[用户任务] --> B[交互意图]
  B --> C[平台表达]
  C --> D[具体界面]
```

- C. 移动端缩小桌面端界面，保持视觉一致
- D. 每个平台独立设计，不共享任何交互规则

### 第二步：为什么不能只写“组件规范”？

很多团队一开始就定义：

- 按钮圆角是多少
- 主色是什么
- 卡片间距是多少
- 输入框长什么样

但真实产品还会遇到：

- 数据加载中怎么办？
- 没有数据怎么办？
- 请求失败怎么办？
- 用户没有权限怎么办？
- 用户正在编辑时网络断了怎么办？

因此设计系统不能只是“组件外观库”，还必须描述：

> **组件在不同状态下如何工作。**

例如一个“提交”按钮至少要考虑：

```text
默认 → 点击中 → 成功
              ↘ 失败 → 可重试
```

这会带来第二条原则：

> **规范状态和行为，比规范静态外观更重要。**

### 第三步：为什么要使用语义令牌？

如果直接写：

```text
蓝色 = #2563EB
```

组件就被绑死在某个具体颜色上。换主题、做深色模式或提高对比度时，会很难维护。

更好的方式是：

```text
color.action.primary
color.surface.default
color.text.muted
color.feedback.error
```

组件只关心“这个颜色承担什么职责”，不关心它具体是蓝色、绿色还是其他颜色。

因此：

> **设计令牌应该描述语义，而不是描述原始值。**

关系可以理解为：

```text
语义令牌 → 主题映射 → 平台组件
```

例如：

```text
color.action.primary
       ↓
浅色主题：深蓝
深色主题：亮蓝
高对比主题：高对比蓝
```
