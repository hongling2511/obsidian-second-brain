# 有损变换策略

## 定义

有损变换策略是pi处理跨模型交互的核心思想：**在数据转换过程中主动接受信息丢失，因为"有损交接"优于"无法交接"。** 当两个系统的能力不兼容时，与其报错中断，不如降级处理，保证通信继续。

这个哲学影响了pi处理thinking blocks、工具调用ID、消息压缩等的每一个决策。

## 核心原理

### 1. 跨模型消息变换：thinking block的降级

不同LLM的能力差异很大。Anthropic的Claude支持thinking blocks（深度思考），但OpenAI的GPT不支持。

问题：当Agent从Claude切换到GPT时，怎样处理thinking blocks？

**方案对比**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 严格 | thinking block不兼容就报错 | 不隐瞒数据丢失 | 用户被迫换回Claude |
| 有损 | 将thinking block降级为纯文本 | 保证兼容性，继续工作 | 失去thinking的结构化信息 |
| 适配器 | 将thinking block转换为<thinking>标签 | 保留信息，近似兼容 | OpenAI不识别标签，无意义 |

**pi的选择**：有损降级

```typescript
function convertToLlm(
  messages: AgentMessage[],
  targetApi: Api
): Message[] {
  return messages.map(msg => {
    if (msg.thinking && !targetApi.supportsThinking) {
      // 有损：将thinking block丢弃或转为文本
      return {
        role: 'user',
        content: `[之前的思考]\n${msg.thinking}\n\n[实际响应]\n${msg.content}`
      }
    }
    // ... 其他情况
  })
}
```

**权衡**：
- 获得：跨模型兼容性，无缝切换
- 放弃：thinking结构化信息丢失

对于编码Agent这种持续对话的场景，能继续工作比保留思考结构更重要。

### 2. Tool Call ID归一化：长度限制的冲突

不同LLM的tool call ID长度限制差异巨大：

- **OpenAI**：最多450字符，支持任意字符
- **Anthropic Claude**：最多64字符，限定字符集

问题：当Agent从OpenAI切换到Claude时，怎样处理那些450字符的tool ID？

**pi的做法**：ID强制归一化

```typescript
function normalizeToolCallId(id: string, targetApi: Api): string {
  const maxLength = targetApi.maxToolCallIdLength
  const allowedChars = targetApi.toolCallIdCharset
  
  // 步骤1：截断
  let normalized = id.substring(0, maxLength)
  
  // 步骤2：去除非法字符
  normalized = normalized.replace(
    new RegExp(`[^${allowedChars}]`, 'g'),
    '_'
  )
  
  // 步骤3：若仍超长，哈希
  if (normalized.length > maxLength) {
    const hash = sha256(id).substring(0, maxLength)
    normalized = `h_${hash.substring(2)}`  // 保证开头是合法的
  }
  
  return normalized
}
```

**代价**：
- tool ID可能冲突（两个不同的长ID映射到同一个短ID）
- 调试困难（看不到原始ID，只看到哈希）
- 需要维护**ID映射表**以支持结果回写

```typescript
// 维护映射表
const idMap = new Map<string, string>()  // 哈希 → 原始ID

// 执行工具时
const hashedId = normalizeToolCallId(originalId, api)
idMap.set(hashedId, originalId)

// 工具返回结果时
const originalId = idMap.get(toolCall.id)  // 恢复原始ID
```

### 3. Compaction压缩：有损总结替代断链

当对话历史过长时，需要压缩（compaction）以节省成本。

问题：怎样压缩而不失去关键信息？

**严格方案**：不压缩，或only压缩已完成的任务
- 优点：完整保留历史
- 缺点：成本持续增长，长对话最终无法运行

**有损方案**：用LLM总结旧消息
```typescript
async function compactMessages(
  messages: AgentMessage[],
  targetLength: number
): Promise<AgentMessage[]> {
  if (messages.length <= targetLength) {
    return messages
  }
  
  // 保留最新的N条消息
  const keepCount = Math.floor(targetLength * 0.3)
  const oldMessages = messages.slice(0, -keepCount)
  const keepMessages = messages.slice(-keepCount)
  
  // 用LLM总结旧消息
  const summary = await llm.call({
    messages: [
      ...oldMessages,
      {
        role: 'user',
        content: '请总结以上对话的关键信息。'
      }
    ]
  })
  
  // 新历史：总结 + 保留的最新消息
  return [
    { role: 'assistant', content: summary },
    ...keepMessages
  ]
}
```

**丢失的信息**：
- 旧消息的细节（具体怎样修复的代码，用户的具体反馈）
- 但保留：做了什么、为什么失败、最终结果

### 4. 文件操作追踪不随压缩丢失

压缩会丢失很多细节，但有一类信息**必须不能丢**：文件修改记录。

pi的做法：**文件操作追踪独立于消息历史**

```typescript
interface AgentState {
  messages: AgentMessage[]          // 可以压缩
  
  readFiles: Set<string>            // 不压缩：永不丢失
  modifiedFiles: Set<string>        // 不压缩：永不丢失
  fileVersions: Map<string, {
    version: number
    hash: string
    timestamp: Date
  }>
}
```

即使对话历史被压缩得面目全非，外部仍可追溯："这个文件被修改过吗？什么时候？哪个版本？"

### 5. isSameModel的严格判断

何时应用有损变换？当且仅当**模型发生了变化**。

```typescript
function isSameModel(api1: Api, api2: Api): boolean {
  // 必须完全匹配，否则认为"换模型了"
  return api1.provider === api2.provider
      && api1.modelId === api2.modelId
      && api1.contextWindow === api2.contextWindow
      && api1.maxTokens === api2.maxTokens
      // ... 所有关键属性
}

// 使用
const switched = !isSameModel(previousApi, newApi)
if (switched) {
  // 应用有损变换
  messages = convertToLlm(messages, newApi)
  messages = compactIfNeeded(messages)
}
```

**为什么这么严格？**

宁可过度降级（不必要的有损变换）也不冒险（漏掉实际的兼容性问题）。

假设从GPT-4-turbo升级到GPT-4o：
- 严格判断：认为换了模型，应用降级
- 宽松判断：认为没换（同一provider），不降级

后者看起来节省了，但如果存在细微的不兼容性，可能导致Agent行为改变（难以调试）。

## 应用场景

### 场景一：API升级

从OpenAI v1升级到v2：
- 消息格式可能改变（有损变换）
- 但保证旧对话仍可继续（通过降级）

### 场景二：模型迁移

从GPT-4迁移到更便宜的模型（如GPT-3.5）：
- 某些高级功能丢失（如vision、thinking）
- 但Agent继续工作，只是能力下降

### 场景三：跨服务集成

从Anthropic API切换到本地部署的开源模型：
- 协议可能不兼容
- 有损变换确保系统不中断

## 设计的深意

为什么pi采用"有损优于无损"的哲学？

### 原因1：实用主义

编码Agent的目标是**完成任务**，不是保留完美的信息。即使有损失，能继续工作就足够了。

### 原因2：演进的现实

LLM能力在持续演进。新模型支持新特性（如vision、thinking），旧模型不支持。系统必须应对这种不兼容性。

"无法交接"（报错中断）是最差的选择，因为用户无法升级、无法尝试新模型。

### 原因3：成本压力

编码Agent的成本压力很大。当token价格波动时，用户可能想临时切换到更便宜的模型。有损变换让这成为可能。

## 相关取舍

**获得**：
- 跨模型兼容性和灵活性
- 系统的韧性（单个决策变化不会中断）
- 成本优化机会

**放弃**：
- 信息完整性
- 调试的清晰性（有损意味着某些上下文永远丢失了）
- 严格的类型安全

## 实践建议

1. **定义哪些数据可以有损** — 思考、详细步骤 → 可有损；文件修改、最终结果 → 不可有损
2. **记录变换操作** — 日志中应该注明"这里应用了有损变换"，便于调试
3. **提供降级提示** — 用户应该知道什么功能被丢失了（如"thinking block已禁用"）
4. **测试兼容边界** — 验证有损变换后的系统行为是否符合预期

## 对比严格的替代方案

| 策略 | 方式 | 何时工作 | 何时失败 |
|------|------|---------|---------|
| 有损变换 | 降级处理 | 99%（除非差异太大） | 极端兼容性差异 |
| 报错中止 | 遇到不兼容就报错 | 用户明确重试 | 常见情况（切换模型时） |
| 双路支持 | 同时支持两套实现 | 完全兼容 | 维护成本爆炸 |
| 严格适配器 | 标准化接口 | 设计完美时 | 新特性出现时 |
