# Agent循环引擎

## 定义

Agent循环引擎是Agent系统的核心执行引擎，以无状态纯函数形式实现LLM调用→工具执行→再调用的循环。它是pi框架中最关键的抽象，定义了Agent如何思考和行动。

## 核心原理

### 1. 双层循环结构

Agent循环包含两个嵌套的循环：

**外层循环**：处理follow-up消息
- 用户/Agent发出新的消息 → 调用内层循环 → 获得响应
- 决定是否继续（基于结束条件）或返回最终结果

**内层循环**：处理tool call和steering消息
```
LLM调用 → 检查是否为tool call
  ├─ 是：执行工具 → 收集结果 → 继续内层循环
  └─ 否：返回外层，考虑是否follow-up
```

关键点在于，内层循环只在处理工具调用和纠正消息时反复运行，避免过度的LLM调用。

### 2. 无状态设计

这是Agent循环引擎最激进的设计决策：**循环本身不持有任何跨次调用的状态**。

```typescript
// 伪代码：无状态循环的签名
async function agentLoop(
  config: AgentLoopConfig,  // 配置注入（包含LLM、工具、提示词等）
  messages: AgentMessage[],  // 输入消息
  onEvent: (event: AgentEvent) => void  // 事件回调
): Promise<void> {  // 注意：返回void，状态通过事件流传递
```

**为什么无状态？**
1. **可测试** — 给定输入和配置，行为完全确定
2. **可分布式** — 无session亲和性，可轻松分散到多个进程/机器
3. **可组合** — 循环可以嵌套、管道化、并联运行
4. **调试友好** — 每次调用可完全重放（给定相同的LLM输出）

**成本**：所有状态管理（会话历史、重试、压缩）必须由外层承载。

### 3. 消息变换管道

循环只在一个地方进行消息变换：**LLM调用边界**。

```
Agent消息 (包含thinking、tool calls等)
    ↓ convertToLlm()
    LLM格式 (model-specific message)
    ↓ LLM API
    LLM响应
    ↓ parseResponse()
    Agent消息
    ↓ 循环继续
```

所有其他操作（工具执行、事件发射）都是幂等的，不改变消息流本身。这个设计让"有损变换"（模型间迁移时丢弃某些功能）变得可控。

### 4. 事件发射：唯一的输出通道

循环的唯一输出是事件流。没有返回值，没有异常，只有事件：

```typescript
enum AgentEventType {
  Started,
  MessageReceived,
  LLMCalled,
  ToolCalling,
  ToolExecuted,
  ToolError,
  ResponseText,
  ThinkingBlock,
  LoopEnded,
  Error,
}
```

这个设计的优点：
- **会话录制** — 所有事件可被持久化
- **实时流式输出** — 前端可逐事件处理，给用户实时反馈
- **观测友好** — 每个事件都可被日志、监控、追踪系统捕捉
- **回放能力** — 给定事件序列可重放整个交互

### 5. "Must Not Throw"契约

循环引擎有一个硬约束：**循环内的所有回调（包括工具执行、LLM调用、消息变换）都不能抛异常**。

```typescript
// 循环看到工具执行失败，不会throw
// 而是发出ToolError事件，继续循环

// LLM API超时，不会throw
// 而是发出Error事件，让配置的retry策略决定

// 消息变换失败（如token限制导致无法压缩），不会throw
// 而是降级处理（有损变换）并继续
```

这个约束来自于"流式事件契约"的要求——异常应该被编码进事件流，而非打破事件流。

## pi中的具体实现

pi-agent-core中的agentLoop约900行代码，包含：
1. 消息队列管理（处理工具返回结果）
2. LLM调用和响应解析
3. 工具执行协调
4. 事件发射
5. 循环终止条件判断

关键特点：
- 没有会话管理 — 会话由上层（pi-ai）维护
- 没有自动重试 — 重试由AgentLoopConfig的回调实现
- 没有自动压缩 — 压缩由transform context回调实现
- 没有plan mode — 规划是一种工具，不是核心功能

## 应用示例

### 场景一：构建自己的Agent框架

如果你要设计一个Agent系统，考虑循环引擎是否应该是无状态的。无状态的优势：
- 支持多个并发Agent运行
- 易于分布式部署
- 测试更简单

代价是上层需要处理会话、上下文管理等。

### 场景二：定制循环行为

pi允许通过AgentLoopConfig注入自定义行为：
- `executeToolFn` — 自定义工具执行（如权限检查、日志记录）
- `beforeToolCall` — 工具调用前的拦截器
- `transformContext` — 改变Agent看到的消息

不需要修改循环本身，只需在配置层扩展。

### 场景三：与其他系统集成

循环的纯函数特性让集成变得简单：
- 调用循环 → 监听事件 → 更新外部系统

例如，可以构建一个"Agent + 数据库 + Web UI"的系统：
1. Web UI 发起请求
2. 服务器调用agentLoop
3. 每个事件更新数据库
4. 前端实时订阅数据库更新

## 相关取舍

**获得**：
- 极致可组合性 — 循环可以嵌套、管道化
- 极致可测试性 — 给定输入和配置，输出完全确定
- 分布式友好 — 无session状态，易于水平扩展

**放弃**：
- 某些便利性 — 会话管理、自动重试、智能压缩都需要外层实现
- 某些安全性 — 无状态意味着无法在循环内验证约束，必须靠外层
- 某些性能优化 — 无法在循环内缓存（缓存会破坏无状态性）

## 实践建议

1. **循环只负责一件事** — 给定输入和配置，产生输出。不要让循环知道"会话"、"用户"、"权限"。
2. **所有策略都通过配置注入** — 重试策略、超时策略、降级策略都应该通过AgentLoopConfig传入。
3. **事件流是唯一真相** — 所有外部状态更新都应该源于事件流，而非循环的返回值。
4. **测试无状态循环很简单** — 构造输入 → 调用循环 → 断言事件序列。
