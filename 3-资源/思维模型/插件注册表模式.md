# 插件注册表模式

## 定义

插件注册表模式是一种运行时扩展机制，通过简单的注册/查找接口实现开放式扩展。新的实现可以随时注册到系统中，核心代码完全不需要因为新增实现而修改。这是实现"开闭原则"的一种优雅方式。

## 核心原理

### 1. 最小化注册表API

最好的API就是最简单的API。pi的api-registry只有四个操作：

```typescript
interface ApiRegistry {
  register(sourceId: string, api: Api): void
  get(id: string): Api | undefined
  list(): Api[]
  unregister(sourceId: string): void
}
```

整个实现只有约98行代码。关键约束：
- **只存储**，不管理生命周期（无初始化、销毁钩子）
- **全局唯一**，同一sourceId只能注册一次（后注册覆盖）
- **原子操作**，注册/注销是原子的，不涉及事务

### 2. 类型擦除与运行时检查

注册表面临一个类型论证的挑战：**如何在通用注册表中存储不同类型的实现？**

pi的解决方案是类型擦除 + 运行时检查：

```typescript
// 注册：接受任何满足接口的对象
registry.register('gpt-4', {
  provider: 'openai',
  modelId: 'gpt-4',
  maxTokens: 8192,
  costPerMTok: 0.03,
})

// 获取：返回通用对象，调用者负责类型安全
const api = registry.get('gpt-4')
if (api && api.provider === 'openai') {
  // TypeScript: 仍需手动类型检查
  const openaiApi = api as OpenaiApi
  // 使用
}
```

**优点**：
- 无需泛型，代码简洁
- 支持跨module的实现（甚至跨package）

**缺点**：
- 失去编译时类型安全
- 调用者需要手动类型守卫

### 3. 延迟加载策略

对于Provider Registry（工具、插件等），pi采用**延迟加载**策略：

```typescript
registry.register('gpt-4-plugin', {
  sourceId: 'gpt-4-plugin',
  load: async () => {
    // 首次调用时才import()，非启动时
    return (await import('./gpt4-plugin')).default
  }
})

// 首次获取时触发import
const plugin = await registry.get('gpt-4-plugin').load()
```

**好处**：
- 启动速度快 — 只加载实际使用的plugin
- 按需依赖 — 不需要在package.json声明所有plugin

**代价**：
- 首次调用有延迟（import网络往返）
- 需要处理加载失败情况

### 4. 批量注销与sourceId

注册表支持以sourceId为单位的批量注销：

```typescript
registry.register('oauth-plugin-v1', {...})
registry.register('oauth-token-v1', {...})
registry.register('oauth-refresh-v1', {...})

// 一次注销整个oauth插件集
registry.unregister('oauth-*')  // 所有以oauth-开头的
```

这种设计的好处：
- **原子性** — 成组的plugin可以同时上线/下线
- **版本管理** — v1下线时自动清理所有v1的东西

### 5. Provider和Api的解耦维度

pi中有两个独立的注册维度：

**Api注册表** — 模型能力（GPT-4、Claude等）
```
openai:gpt-4 → { provider: 'openai', modelId: 'gpt-4', ... }
anthropic:claude-opus → { provider: 'anthropic', modelId: 'claude-opus', ... }
```

**Provider注册表** — 工具集合（Browser、Bash等）
```
browser → BrowserProvider实例
bash → BashProvider实例
code-execution → CodeExecutionProvider实例
```

这样的分离让：
- 新增模型只需注册Api，不需要修改Provider
- 新增工具只需注册Provider，不需要修改其他工具

## pi中的具体应用

### 场景一：工具扩展
pi-coding-agent内置几个核心工具（bash、read、write等）。用户可以通过registry添加自己的工具：

```typescript
const toolRegistry = new ProviderRegistry()

// 内置工具
toolRegistry.register('read', ReadProvider)
toolRegistry.register('write', WriteProvider)

// 用户自定义工具
toolRegistry.register('database', DatabaseProvider)
toolRegistry.register('slack', SlackProvider)
```

核心Agent代码完全不知道有这些额外工具。

### 场景二：模型扩展
支持新的LLM模型（如DeepSeek、Qwen）时，只需：
```typescript
apiRegistry.register('deepseek:v3', {
  provider: 'deepseek',
  modelId: 'v3',
  costPerMTok: 0.0001,
})
```

pi-agent-core、pi-ai的代码无需修改。

### 场景三：运行时插件加载
某些场景需要运行时加载plugin（如Lambda函数启动时加载用户plugin）：

```typescript
const userPlugins = await fs.readdir('/opt/plugins')
for (const plugin of userPlugins) {
  const { default: impl } = await import(`/opt/plugins/${plugin}`)
  registry.register(plugin, impl)
}
```

## 相关取舍

**获得**：
- **无限扩展性** — 添加新的tool/provider/model无需修改核心代码
- **清晰的约束** — 实现必须满足特定接口
- **版本独立** — 不同实现可有不同版本号

**放弃**：
- **静态分析能力** — 工具集、模型集在运行时才完全已知
- **编译时安全** — 无法在编译期验证所有tool都实现了接口
- **性能可预测性** — 首次加载plugin有延迟

## 与其他扩展方式的对比

| 方式 | 代码改动 | 复杂度 | 运行时性能 | 应用场景 |
|------|---------|--------|-----------|---------|
| 注册表 | 零 | 低 | 中等 | 插件系统、多实现选择 |
| 工厂函数 | 小 | 中 | 高 | 对象创建的灵活性 |
| 依赖注入 | 小 | 高 | 高 | 大型框架、复杂关系 |
| Decorator | 无 | 低 | 低 | Python、Java的优先选择 |
| 策略模式 | 小 | 低 | 高 | 单一维度的变化 |

## 实践建议

1. **保持注册表简洁** — 只存储必要的数据，生命周期管理交给使用者。
2. **定义清晰的接口** — 实现必须满足的合约很关键（pi的Api接口有5个必填字段）。
3. **提供注册检查** — 可以添加register前的验证（检查sourceId是否重复、接口是否完整）。
4. **考虑优先级顺序** — 当多个实现满足条件时，如何选择？（list()的顺序很重要）
5. **文档化加载路径** — 使用者需要明确知道如何注册新实现。

## 扩展思考

### sourceId的命名约定
pi推荐的命名：`namespace:name:version`
```
openai:gpt-4:v20250412
anthropic:claude-opus:v20250101
custom:mymodel:v1
```

### 冲突处理
如果两个来源注册相同的sourceId：
- 后注册覆盖前一个 — 简单但可能隐藏问题
- 抛异常拒绝 — 安全但不灵活
- 合并配置 — 复杂但强大

pi选择"后注册覆盖"，让用户有能力override默认实现。

### 注册表的作用域
- 全局注册表：所有Agent共享工具集
- 局部注册表：特定Agent的私有工具集

pi支持两种，通过参数化AgentLoopConfig来选择。
