# 流式事件契约

## 定义

流式事件契约是pi框架的通信基础：**所有交互都是流式事件，没有"一次性返回"。错误被编码进事件流而非通过异常抛出。** 这个设计影响了整个系统的每一层，从Agent循环到Web前端。

## 核心原理

### 1. EventStream：lock-free异步通道

EventStream是一个简单但强大的数据结构，用约50行代码实现：

```typescript
interface EventStream {
  // 生产者接口
  emit(event: AgentEvent): void
  complete(result?: AgentResult): void
  error(error: Error): void
  
  // 消费者接口
  [Symbol.asyncIterator](): AsyncIterator<AgentEvent>
  next(): Promise<{ value: AgentEvent | AgentResult; done: boolean }>
  
  // 等待结果
  result(): Promise<AgentResult>
}
```

**实现方式**：
- 内部用**queue**存储事件
- 消费者通过**async iterator**遍历
- 使用**waiting消费者模式**（类似Go的channel）：生产者写入事件，消费者立即获通知

**关键特点**：
- 无锁 — 利用JavaScript单线程特性，不需要互斥锁
- 背压处理 — 如果消费者跟不上，事件堆积在queue
- 多消费者支持 — 多个消费者可独立迭代同一流

### 2. 12种事件类型覆盖整个生命周期

pi定义了12种事件，覆盖Agent从开始到结束的整个过程：

```typescript
enum AgentEventType {
  // 生命周期
  Started,           // Agent开始运行
  LoopEnded,        // 循环结束（可能还有follow-up）
  
  // 消息相关
  MessageReceived,  // 接收用户消息
  ResponseStarted,  // 开始生成响应
  
  // LLM相关
  LLMCalled,        // 调用LLM
  
  // 工具相关
  ToolCalling,      // 工具调用开始
  ToolExecuted,     // 工具执行完成
  ToolError,        // 工具执行失败
  
  // 内容流
  TextChunk,        // 纯文本响应片段
  ThinkingBlock,    // LLM的thinking内容
  
  // 错误
  Error,            // 系统错误
  
  // 特殊
  Cost,             // 成本更新
}
```

每个事件都有**时间戳**和**元数据**：

```typescript
interface AgentEvent {
  type: AgentEventType
  timestamp: Date
  metadata?: Record<string, any>
  
  // 具体事件的payload
  content?: string          // for TextChunk
  thinking?: string         // for ThinkingBlock
  tool?: ToolCall          // for ToolCalling
  result?: ToolResult      // for ToolExecuted
  error?: Error            // for Error/ToolError
  costDelta?: number       // for Cost
}
```

### 3. "Must Not Throw"契约

这是流式事件契约的硬约束：**所有StreamFn回调都必须不抛异常**。

```typescript
type StreamFn = (emit: (event: AgentEvent) => void) => Promise<void>

// 这个StreamFn违反了契约：
const badStreamFn: StreamFn = async (emit) => {
  emit({ type: 'Started' })
  throw new Error('Oops!')  // 违反：不能抛异常
}

// 正确的方式：
const goodStreamFn: StreamFn = async (emit) => {
  emit({ type: 'Started' })
  try {
    // 做某事
  } catch (e) {
    emit({ type: 'Error', error: e })  // 编码进事件流
  }
}
```

为什么这么严格？因为一旦抛异常，事件流就被中断了，后续消费者无法获得任何信息。

类似地，`convertToLlm`、`transformContext`等回调也都不能抛异常。

### 4. Stream vs Complete：语法糖关系

`complete()`是`stream()`的便利包装：

```typescript
// 本质上等同于：
async function stream(fn: StreamFn): EventStream {
  const stream = new EventStream()
  
  // 后台运行StreamFn
  fn((event) => stream.emit(event))
    .then(() => stream.complete())
    .catch((e) => stream.error(e))
  
  return stream
}

// 而complete()是：
async function complete(fn: StreamFn): AgentResult {
  const stream = await stream(fn)
  return stream.result()  // 等待完成，返回最终结果
}
```

使用者根据需求选择：
- 需要实时反馈 → 用`stream()`逐事件处理
- 需要最终结果 → 用`complete()`等待完成

### 5. 事件流让三件事成为可能

#### 可能性1：会话录制与回放

所有事件可被持久化到数据库：

```typescript
const stream = agent.stream(userMessage)
for await (const event of stream) {
  // 实时保存到数据库
  await db.events.create({
    sessionId,
    event,
    timestamp: event.timestamp
  })
  
  // 实时推送给前端
  ws.send(JSON.stringify(event))
}
```

未来可以回放这个会话：

```typescript
const events = await db.events.find({ sessionId })
for (const event of events) {
  // 重现整个交互过程
  frontend.display(event)
}
```

#### 可能性2：分布式追踪

事件流与分布式追踪系统无缝集成：

```typescript
const traceId = crypto.randomUUID()
const stream = agent.stream(message, { traceId })

for await (const event of stream) {
  tracer.recordEvent({
    traceId,
    spanId: event.metadata?.toolCallId,
    name: event.type,
    timestamp: event.timestamp
  })
}
```

这样每个Agent运行都可被完整追踪，对性能分析、故障排查至关重要。

#### 可能性3：自适应流控与背压

消费者可以根据处理能力控制生产者：

```typescript
const stream = agent.stream(message)
let queuedEvents = 0

for await (const event of stream) {
  queuedEvents++
  
  // 异步处理
  process(event).then(() => {
    queuedEvents--
    if (queuedEvents > 10) {
      // 背压：消费者处理不过来，让生产者慢下来
      waitForCapacity()
    }
  })
}
```

### 6. 事件流的消费模式

典型的消费模式包括：

**模式1：状态机累积**
```typescript
const state = {
  messages: [],
  thinking: '',
  lastTool: null,
  totalCost: 0
}

for await (const event of stream) {
  switch (event.type) {
    case 'MessageReceived':
      state.messages.push(event.content)
      break
    case 'ThinkingBlock':
      state.thinking += event.thinking
      break
    case 'Cost':
      state.totalCost += event.costDelta
      break
  }
}
```

**模式2：管道变换**
```typescript
// 链式处理：事件流 → 过滤 → 变换 → 消费
for await (const event of stream
  .filter(e => e.type !== 'Cost')  // 忽略成本事件
  .map(e => enrichEvent(e))         // 添加元信息
) {
  handleEvent(event)
}
```

**模式3：事件分流**
```typescript
// 根据事件类型分别处理
const streamPromises = [
  handleTextChunks(stream),      // 给UI流式渲染
  recordMetrics(stream),         // 记录指标
  logDebug(stream),              // 写日志
  updateDatabase(stream)         // 更新数据库
]
await Promise.all(streamPromises)
```

## 与其他设计的对比

| 设计 | 返回方式 | 错误处理 | 实时性 | 复杂度 |
|------|---------|---------|--------|--------|
| 流式事件 | 事件流 | 事件编码 | 优秀 | 中等 |
| Promise单返回 | Promise<Result> | try/catch | 差 | 低 |
| 回调函数 | onSuccess/onError | 回调地狱 | 中等 | 高 |
| async/await | await result | try/catch | 差 | 低 |
| WebSocket长连接 | 消息 | 消息内编码 | 优秀 | 高 |

## 应用示例

### 场景一：Web UI的实时显示

```typescript
const response = document.getElementById('response')
const thinkingArea = document.getElementById('thinking')

const stream = await agent.stream(userInput)
for await (const event of stream) {
  switch (event.type) {
    case 'TextChunk':
      response.innerHTML += escapeHtml(event.content)
      break
    case 'ThinkingBlock':
      thinkingArea.innerHTML = event.thinking
      break
    case 'ToolCalling':
      showToolBadge(event.tool.name)
      break
    case 'Cost':
      updateCostDisplay(event.costDelta)
      break
  }
}
```

### 场景二：CLI的进度显示

```typescript
const spinners = {}
const stream = await agent.stream(task)

for await (const event of stream) {
  switch (event.type) {
    case 'ToolCalling':
      spinners[event.tool.name] = ora(event.tool.name).start()
      break
    case 'ToolExecuted':
      spinners[event.tool.name].succeed()
      break
    case 'TextChunk':
      process.stdout.write(event.content)
      break
  }
}
```

### 场景三：监控系统的指标收集

```typescript
const metrics = {
  totalTokens: 0,
  toolCount: 0,
  errorCount: 0,
  duration: 0
}

const start = Date.now()
const stream = await agent.stream(query)

for await (const event of stream) {
  metrics.duration = Date.now() - start
  
  if (event.type === 'LLMCalled') {
    metrics.totalTokens += event.metadata?.tokens || 0
  } else if (event.type === 'ToolExecuted') {
    metrics.toolCount++
  } else if (event.type === 'Error') {
    metrics.errorCount++
  }
}

// 发送给监控后端
await prometheus.recordMetrics(metrics)
```

## 相关取舍

**获得**：
- 完全解耦 — 生产者不知道消费者，反之亦然
- 可观测性 — 每个事件都可被日志、追踪、监控系统捕捉
- 实时性 — 消费者可逐个处理事件，无需等待完成
- 灵活组合 — 多消费者可并发处理同一流

**放弃**：
- 简单性 — 消费者需要维护状态机
- 类型安全 — 事件类型动态，难以编译时验证
- 内存效率 — 事件堆积会占用内存

## 实践建议

1. **定义清晰的事件类型** — 每个事件应该代表一个原子操作，不应该过于细粒度或过于粗粒度。
2. **include足够的元数据** — 消费者可能需要关联上下文（tool ID、错误堆栈等）。
3. **考虑事件顺序** — 消费者应该能依赖事件的先后顺序（如：ToolCalling一定在ToolExecuted之前）。
4. **背压设计** — 生产者应该能应对消费者跟不上的情况。
