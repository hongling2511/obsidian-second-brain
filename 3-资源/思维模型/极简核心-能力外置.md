# 极简核心-能力外置

## 定义

这是pi框架最核心的设计哲学：**系统的核心只定义协议和基本抽象，所有可选能力通过外部机制（extension、skill、callback）注入**。核心不是一个充满功能的框架，而是一个极简的引擎，定义了Agent思考的规则，但不定义Agent能做什么、怎么做。

## 核心原理

### 1. pi的三件事

pi核心只做三件事，其他一切都是可选的：

```
┌─────────────────────────────────────┐
│  pi核心（~3000行代码）               │
├─────────────────────────────────────┤
│ 1. 调用LLM                           │
│ 2. 跑循环（工具执行→反馈→再调用）    │
│ 3. 管理对话状态（消息、会话）        │
└─────────────────────────────────────┘
   ↑       ↑       ↑       ↑
   │       │       │       │
扩展点：使用什么模型？ 有什么工具？
        怎样提示词？   如何权限控制？
```

对比市场上的竞品（Claude Code、Cursor、Aider），这些工具通常有10000+行的内置功能。pi的策略是激进地剥离，只保留最小化必要。

### 2. "不内建"的三个判断标准

pi的核心开发者在决定"某功能应该内建还是外置"时，遵循三个标准：

**标准1：是否产品相关？**
- 内建：无关。如Agent循环、消息编解码是所有Agent产品的共性
- 外置：产品相关。如"支持代码补全建议"只有IDE版本需要

**标准2：有多少种合理实现？**
- 内建：一种。如Agent循环的主流模式只有一种
- 外置：多种。如权限控制可以有黑名单、白名单、成本限制等多种方式

**标准3：需要系统级的一致性吗？**
- 内建：是。如状态管理必须贯穿全系统
- 外置：否。如工具日志可以每个产品独立决定

### 3. 四个反主流选择

基于这个哲学，pi做了四个与竞品完全相反的设计决策：

#### 决策1：不内建Sub-Agents

市场期望：Agent应该能自动分解任务，创建sub-agents并行工作。

pi的决策：Sub-agents是可选的，通过"创建agent工具"实现。

```typescript
// 反面例子：框架式
agent.createSubAgent('task-1', 'analyze code')
agent.createSubAgent('task-2', 'write tests')
await Promise.all([...])  // 框架管理并行

// pi的方式：协议式
// Agent看到一个"create-agent"工具，决定自己何时用
const newAgent = tools.createAgent({
  name: 'analyzer',
  tools: [...],
  instructions: '...'
})
const result = await newAgent.complete(...)
```

好处：Agent有完全的控制权；坏处：需要Agent学会何时、怎样使用sub-agents。

#### 决策2：不内建MCP（Model Context Protocol）

MCP是Anthropic最新推出的标准，让工具作为独立进程运行。

pi的态度：MCP是一种工具实现方式，但不是唯一方式。内建MCP会限制工具的其他可能性。

取而代之，pi提供：
- 工具的统一接口（ToolProvider）
- 关键hook点（beforeToolCall、executeToolFn）
- 让使用者自由选择如何实现工具（进程内、MCP、HTTP、数据库）

#### 决策3：不内建权限弹窗

大多数Agent框架有"请求权限"的弹窗机制。

pi的设计：没有固定的权限弹窗。而是通过callbacks：

```typescript
const agentConfig = {
  beforeToolCall: async (toolCall) => {
    // 返回false阻止执行，或返回新的参数
    if (toolCall.name === 'delete' && cost > $100) {
      return false  // 拒绝
    }
    return toolCall
  }
}
```

上层应用（Web UI、CLI）基于这个回调实现自己的权限策略。

#### 决策4：不内建Plan Mode

Plan Mode（先规划后执行）是一个常见特性。

pi的决策：规划是一个工具，不是核心功能。

```typescript
// 如果Agent想规划，它调用规划工具
const plan = await tools.makePlan(userRequest)
// 然后逐步执行
for (const step of plan) {
  await agent.execute(step)
}
```

### 4. 三个回调控制全部行为

代替内建的各种功能，pi提供三个关键回调：

**execute()**：做什么
```typescript
execute: async (toolCall: ToolCall) => {
  // 核心问题：这个工具调用应该执行吗？
  // 可以检查：成本、权限、工具存在性、速率限制
  if (!canAfford(toolCall)) return { error: '成本过高' }
  return actuallyExecute(toolCall)
}
```

**beforeToolCall()**：能不能做
```typescript
beforeToolCall: async (toolCall: ToolCall) => {
  // 问user确认吗？修改参数吗？
  const confirmed = await askUser(`执行${toolCall.name}?`)
  if (!confirmed) return null
  
  // 或者修改工具调用
  toolCall.params.timeout = Math.min(toolCall.params.timeout, 5000)
  return toolCall
}
```

**transformContext()**：看到什么
```typescript
transformContext: async (messages: AgentMessage[]) => {
  // 隐藏敏感信息、截断长消息、添加系统提示
  return messages.map(m => sanitize(m))
}
```

这三个回调是Agent能力扩展的关键杠杆。

### 5. 代价：上手难、重复劳动、文档负担、调试困难

极简核心不是免费的。代价很大：

**上手成本高** — 新用户需要理解整个系统才能定制，不能依赖"框架最佳实践"。

**重复劳动** — 多个产品都想要权限弹窗、都想要成本限制，但每个都要自己实现。

**文档负担** — 需要大量文档解释"这个能力怎么实现"，不像框架可以说"这是内置的"。

**调试困难** — 问题出现时，是框架bug还是用户callback bug？责任边界模糊。

pi的态度：这些代价是值得的，因为换来了终极的灵活性。

## 应用示例

### 场景一：Claude Code的权限控制

Claude Code作为IDE插件，需要防止Agent不小心修改用户生产代码。

```typescript
const config = {
  beforeToolCall: async (call) => {
    if (call.name === 'write') {
      const path = call.params.path
      const isProduction = path.includes('/src/') && !isDev()
      
      if (isProduction) {
        // 不是拒绝，而是要求确认
        return await vscode.window.showWarningMessage(
          `修改生产代码？${path}`,
          '确认', '取消'
        ) === '确认' ? call : null
      }
    }
    return call
  }
}
```

### 场景二：pi CLI的成本限制

CLI版本想要限制单次运行的API成本（比如最多花$1）。

```typescript
const config = {
  execute: async (toolCall) => {
    const cost = estimateCost(toolCall)
    if (totalCost + cost > $1) {
      return { error: '成本限制已达' }
    }
    totalCost += cost
    return actuallyExecute(toolCall)
  }
}
```

### 场景三：Slack版本的速率限制

Slack Bot版本需要防止同一用户频繁触发Agent。

```typescript
const userLastCall = new Map()
const config = {
  beforeToolCall: async (call) => {
    const userId = getCurrentUser()
    const lastTime = userLastCall.get(userId) || 0
    const timeSinceLastCall = Date.now() - lastTime
    
    if (timeSinceLastCall < 5000) {  // 5秒限制
      return null  // 拒绝调用
    }
    userLastCall.set(userId, Date.now())
    return call
  }
}
```

## 评估自己的系统

当设计新的Agent系统或扩展现有系统时，问自己：

| 功能 | 问题 | pi的答案 | 你应该的答案 |
|------|------|---------|------------|
| 权限控制 | 有多种实现吗？ | 是（黑/白名单/成本/速率限制） | 同意 → 外置 |
| 对话压缩 | 所有产品都需要吗？ | 是（省成本） | 需要 → 内建callback |
| Sub-agents | 有多种实现吗？ | 是（顺序/并行/树形） | 同意 → 外置 |
| 工具执行 | 一致性关键吗？ | 是 | 同意 → 内建 |
| 消息编解码 | 一致性关键吗？ | 是 | 同意 → 内建 |

## 相关取舍

**获得**：
- 极致灵活性 — 几乎任何定制都可能实现
- 学习价值高 — 理解核心后能快速掌握全系统
- 长期可维护性 — 核心代码少，bug更少

**放弃**：
- 用户友好度 — "开箱即用"很难
- 快速原型化 — 每个新功能都需要自己实现逻辑
- 社区标准 — 没有"官方推荐做法"，用户各自为政
