## 📄 概述

《pi设计艺术》的前三章构建了整个pi框架的哲学基础和物理架构。作者通过与业界主流框架（LangChain、Vercel AI SDK、CrewAI）的对比，阐述了pi作为**运行时而非调用库**的核心定位，进而衍生出了"四层洋葱架构"和"7个npm包的分层纪律"两大系统设计原则。

这不仅是一次技术选型的说明，更是一套**关注点分离**和**接口隔离**的设计哲学体现。

## 📑 主要内容

### 第1章：Pi是运行时，而非调用库

**核心论点**：pi的定位差异决定了其整个架构的层级划分方式。

**与其他框架的对比**：

| 框架 | 定位 | 核心职责 | 状态管理 |
|------|------|---------|---------|
| **LangChain** | 链式编排库 | 通过Chain和Runnable组装流程 | 由使用者维护 |
| **Vercel AI SDK** | 流式调用库 | 统一不同provider的流式接口 | 轻量级，client-centric |
| **CrewAI** | 多Agent编排库 | 通过Task和Crew定义Agent协作 | Agent间同步开销大 |
| **pi** | Agent运行时 | 提供完整的Loop、Event、State机制 | 内置状态机，对外隐藏 |

pi的"运行时"定位意味着：
1. **循环管理权**：pi掌握Agent循环的完整控制流，而不是被调用者驱动
2. **状态隐藏**：内部状态对调用侧完全不可见，只暴露事件流
3. **约束编码**：通过"Must not throw"等契约，强制规范执行规则

**四层洋葱架构**：

```
┌─────────────────────────────┐
│    4. 产品壳层              │  具体应用（Web、CLI、IDE插件等）
├─────────────────────────────┤
│    3. pi-coding-agent       │  编码Agent具体实现
├─────────────────────────────┤
│    2. pi-agent-core         │  通用Agent循环引擎（~1859行）
├─────────────────────────────┤
│    1. pi-ai                 │  大模型调用统一面（Provider、OAuth等）
└─────────────────────────────┘
```

**关键设计原则**：
- **分层隔离**：每层只知道其下一层的接口，不感知更下层的实现细节
- **向下依赖**：上层依赖下层，下层绝不依赖上层（无循环依赖）
- **接口最小化**：每层对上暴露的接口严格受限，只暴露必要能力

这种设计的收益：某个产品壳可轻松切换coding-agent实现（例如从TypeScript改为Python），只要遵守接口契约即可。

### 第2章：7个npm包的分层纪律

**包划分的唯一原则**："当且仅当两段代码有不同的使用者时，才应该分为两个包"。

这个看似简单的原则，导出了pi的包结构：

```
pi-ai
├── pi-core-types          # 全局类型定义（所有包共用）
├── pi-provider-*          # Provider层（注册特定模型供应商）
├── pi-ai-core             # 统一调用面（Route、OAuth、流变换）
├── pi-agent-core          # Agent循环引擎（Loop、Event、State）
├── pi-coding-agent        # 编码Agent实现（与业务逻辑耦合）
└── pi-product-*           # 产品壳（Web、CLI等）
```

**lockstep版本策略**：所有7个包版本号始终一致。这不是为了方便，而是为了强制约束——一旦某个包需要breaking change，整个生态一起升级，避免了"依赖地狱"。

**依赖方向的纪律**：
- `pi-provider-*` → `pi-core-types`（单向）
- `pi-ai-core` → `pi-core-types` + `pi-provider-*`
- `pi-agent-core` → `pi-ai-core`（依赖下层不反向）
- `pi-coding-agent` → `pi-agent-core`
- `pi-product-*` → `pi-coding-agent`（不能跨层依赖）

**包的精简程度**：
- `pi-agent-core`仅~1859行代码（含注释），通过极致的接口隔离实现
- 每个provider实现通常只需100-300行（共享协议和registry）

这样的包划分让新贡献者可以：
1. 添加新Provider仅需关注~4个关键点（兼容协议即可）
2. 修改Agent逻辑而不影响Provider生态
3. 理解某个包时，完全不需要理解其他包

### 第3章：阅读仓库的正确方式

**骨架优先原则**：不要从某个provider的实现开始读，这样容易迷失在细节。应该按这个顺序：

1. **types/**
   - 了解全局的数据结构：`Message`、`Model`、`EventStream` 等
   - 这些类型定义是所有层级通信的词汇表

2. **api-registry.ts**
   - 理解Provider如何注册和路由
   - 泛型`Model<TApi>`如何传播协议信息
   - 类型擦除的桥接机制

3. **agent-loop/**
   - 核心的Loop函数签名和事件发射机制
   - 双层循环结构（内层tool call，外层follow-up）
   - "Must not throw"契约和错误编码进事件流

4. **message-transform/**
   - 不同provider间消息的适配
   - thinking block、tool call的有损变换

5. **provider实现**
   - 此时理解具体某个provider如何适配通用协议
   - 代码量少且模式重复，容易理解

**阅读技巧**：
- 使用IDE的类型追踪功能（Ctrl/Cmd+点击）追踪泛型参数的流向
- 关注interface定义，忽略具体实现细节（第一遍）
- 找出每个模块暴露的"5个关键函数"，这是接口契约的核心

## 💡 关键洞见

1. **运行时vs框架库的选择**：运行时能控制循环，从而编码约束（如"Must not throw"）；框架库则被动等待回调。pi选择运行时意味着放弃"让用户自己管理循环"的自由，换来了"可靠、可测试、组合性强"。

2. **接口隔离的力量**：pi-agent-core只需要1859行代码，核心秘密是每层接口都极其清晰。这让代码读者和维护者可以轻松理解边界。

3. **锁步版本的隐形收益**：表面上是"版本管理的方便"，实质是"强制所有包在同一代际上演进"，从而避免了跨版本的兼容性噩梦。

4. **包划分不是为了重用**：pi的包不是为了复用而分（事实上pi-coding-agent很难跨项目复用），而是为了**关注点分离**——让某个包的贡献者只需关注他的领地。

## ⚙️ 实践应用

1. **为pi贡献新Provider**：首先理解`Model<TApi>`泛型如何定义协议，然后在provider中实现这个TApi接口，最后在registry中注册。不需要改动核心循环。

2. **理解某个已有Provider的bug**：沿着"api-registry → provider具体实现 → message-transform（如有）"的路径追踪，避免涉足Agent循环层。

3. **扩展Agent能力（如添加新的工具执行策略）**：这属于"修改循环"，必须在pi-agent-core层面，会涉及lockstep版本升级，需要整个生态对齐。
