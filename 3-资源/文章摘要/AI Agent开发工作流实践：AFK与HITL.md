# AI Agent 开发工作流实践：AFK 与 HITL

## 一句话总结

AI Agent 开发不是把规格说明丢给模型，然后等它吐出完整代码。更稳的做法是把工作拆成两类：人必须参与判断的 HITL 任务，以及边界清楚后可以交给 Agent 独立执行的 AFK 任务。人负责方向、边界、品味和验收，Agent 负责在明确反馈闭环里实现、测试和修复。

这套方法来自 Matt Pocock 近期关于 Claude Code 和 AI coding workflow 的几场分享。它看起来是在讲 AI 工具，底层其实还是经典软件工程：需求澄清、领域语言、垂直切片、测试驱动、代码审查、架构边界和反馈循环。

## 两个核心概念

### AFK：离开键盘后还能继续推进的任务

AFK 是 Away From Keyboard，意思是人可以暂时离开键盘。放在 AI Agent 开发里，AFK 任务指的是已经有清楚目标、边界、验收标准和反馈方式的任务。Agent 可以自己读 issue、改代码、跑测试、提交结果，人在之后回来审查。

典型 AFK 任务包括：

- 根据一个写清楚的 issue 实现一个垂直切片
- 用 TDD 写一个失败测试，再补实现让测试通过
- 修复明确的测试失败、类型错误、lint 错误
- 根据 QA 反馈修一个具体 bug
- 对最近几次提交做自动代码审查

AFK 不等于完全不用管。它只是把人的参与点从“实时盯着写代码”改成“提前定义任务，事后审查结果”。

### HITL：人必须在循环里的任务

HITL 是 Human In The Loop，意思是人在决策循环里。只要任务涉及产品取舍、领域理解、架构边界、UI 品味、命名、风险判断，就不适合直接交给 Agent 自己决定。

典型 HITL 任务包括：

- 把模糊想法澄清成可执行需求
- 回答“为什么要做”，而不只是描述“要做什么”
- 统一领域语言，比如 ghost lesson、materialize、course version 这类概念
- 判断 PRD 应该包含哪些范围，哪些应该排除
- 审查 PRD 拆出来的 issue 是否切得合理
- 对 UI 做原型选择和体验判断
- 手动 QA，发现真实使用中的问题

Matt 的核心判断很直接：规划、澄清和 QA 必须有人参与；实现阶段在条件成熟后可以交给 Agent。

## 完整工作流

```text
想法 / brief
  ↓
Grill Me：让 AI 反复追问，和人达成共同理解
  ↓
PRD：沉淀目的地
  ↓
PRD to Issues：拆成可领取、可验证、可并行的任务
  ↓
AFK Agent Loop：Agent 按 issue 实现
  ↓
TDD / 类型检查 / 测试 / 自动 review
  ↓
人工 QA
  ↓
把 QA 问题重新变成 issue，继续进入 Agent Loop
```

这个流程里，前半段是人的白天工作，后半段是 Agent 的夜间工作。人不是把自己从开发里拿掉，而是从“逐行写实现”转向“管理反馈、边界和质量”。

## 第一步：用 Grill Me 澄清需求

Matt 很少让 AI 一上来就写计划。他会先用一个很短的 `Grill Me` skill，让 AI 围绕一个想法持续追问，直到双方形成共同理解。

这个阶段的目标不是产出文档，而是暴露分歧和未知。比如要做课程系统里的 ghost course，AI 会问：

- ghost course 是否允许 real lesson？
- 如果用户在 ghost course 里创建 real lesson，是否要立刻选择文件路径？
- 删除 real lesson 时，是只删数据库，还是连磁盘文件一起删？
- course version 在 ghost course 里是否仍然存在？
- 什么情况下一个 real course 会重新变回 ghost course？

这些问题很难靠一次 prompt 想全。AI 的价值在这里不是替人拍板，而是持续逼近决策树的分叉点。人回答后，AI 再沿着新的分叉继续问。

这一阶段有一个很重要的输入：解释为什么。只告诉 AI “我要加一个按钮”，它只能照字面实现；告诉它为什么这个流程现在麻烦，它才可能提出更合适的产品路径。

## 第二步：建立领域语言

Matt 在真实项目里会维护类似 DDD 里的 ubiquitous language，也就是领域通用语言。它让人和 Agent 对同一个词有同一个理解。

比如：

- ghost lesson：数据库里存在，但文件系统里还没有实体的 lesson
- materialize：把 ghost lesson 或 ghost course 写入文件系统，变成真实资源
- course version：课程内容的版本记录，用来发布和生成 changelog

这类词一旦稳定下来，后面的 prompt、PRD、issue、测试名、函数名都会更清楚。Agent 搜代码时也更容易找到相关位置。相比反复解释“那个还没写到磁盘里的课程”，一个稳定术语能显著降低沟通成本。

## 第三步：写 PRD，但不要迷信 PRD

Grill Me 结束后，可以让 AI 把对话整理成 PRD。PRD 在这个流程里是“目的地文档”，它回答的是我们要到哪里。

一个够用的 PRD 通常包含：

- 问题陈述：现在用户遇到什么麻烦
- 解决方案：我们打算改变什么
- 用户故事：用户应该能完成哪些行为
- 实现决策：哪些设计已经拍板
- 测试决策：哪些行为必须被测试覆盖
- Out of scope：哪些事这次不做

Matt 不会把 PRD 当成真理。他甚至不太花时间逐字审 PRD，因为前面的 Grill Me 已经让人和 AI 对齐。PRD 的作用是压缩共同理解，供后续拆 issue 使用。

这里有个反直觉点：完成后的 PRD 不一定适合长期留在仓库里。旧 PRD 很容易变成 doc rot，代码已经变了，需求也变了，但 Agent 以后看到旧文档，还可能误以为它是当前事实。Matt 更倾向于把 PRD 放在 GitHub issue 里，完成后关闭，让它有明确的生命周期。

## 第四步：把 PRD 拆成垂直切片

AI 很容易把任务按层拆：

```text
第一步：改数据库
第二步：改 API
第三步：改前端
第四步：补测试
```

这种拆法的问题是反馈太晚。前两步做完时，系统还不能被真实使用，直到前端接上才知道设计是否成立。

Matt 更推崇 vertical slice，也就是垂直切片。每个 issue 尽量贯穿数据库、服务、API、UI 和测试，做完以后能验证一小段完整体验。

比如“创建 ghost course”这个功能，可以拆成：

- 用户能在创建课程弹窗里创建一个 ghost course
- 数据库允许 course file path 为空
- 创建成功后跳转到新课程页面
- UI 不暴露 ghost course 这种内部术语
- 对应服务和 reducer 有测试覆盖

这比“先改 schema”更接近真实反馈。每个切片都像一颗 tracer bullet，可以让团队尽早看到方向是否打偏。

## 第五步：把 issue 标成 AFK 或 HITL

不是所有 issue 都应该让 Agent 做。拆完任务后，可以给每个任务一个执行属性。

| 任务类型 | 适合谁做 | 判断标准 |
|----------|----------|----------|
| 需求澄清 | HITL | 需要产品、领域或用户判断 |
| 方案研究 | HITL 为主 | 需要取舍、比较和确认方向 |
| UI 原型 | HITL 为主 | 需要人看效果、选方向 |
| 垂直切片实现 | AFK | 验收标准清楚，反馈闭环明确 |
| 明确 bug 修复 | AFK | 有复现步骤和期望行为 |
| 手动体验验收 | HITL | 需要品味、耐心和真实使用感 |
| 自动测试补齐 | AFK | 行为边界明确 |
| 架构边界调整 | HITL 为主 | 需要接口设计和长期判断 |

这张表的价值不在格式，而在提醒自己：别把需要判断的事伪装成执行任务。

## 第六步：让 Agent 在 AFK Loop 里实现

当 issue 足够清楚后，Agent 可以进入 AFK loop。一个简单版本的循环是：

```text
读取未完成 issue
选择一个不被阻塞的 AFK issue
探索代码库
确认要改的模块和接口
用 TDD 写失败测试
实现功能
跑测试、类型检查、lint
提交代码
关闭 issue 或留下结果说明
继续下一个 issue
```

Matt 还展示过一种更自动化的做法：把每次 Agent 执行放在独立 worktree 或 Docker sandbox 里，让它在隔离环境中改代码、生成提交，再把 patch 应用回本地仓库。这让多个 Agent 并行工作更安全。

并行不是越多越好。只有当 issue 之间有清楚的阻塞关系，而且任务切片相对独立时，多个 Agent 同时跑才有意义。否则并行只会把冲突提前放大。

## 第七步：用 TDD 给 Agent 反馈

Matt 认为 TDD 是提高 Agent 输出质量最稳定的方法之一。原因很简单：AI 如果没有反馈，就只能凭感觉写代码。测试、类型检查、lint、构建错误，都是它能理解和修正的反馈。

TDD 对 Agent 尤其有用，因为它限制了“先实现一堆，再补看起来能过的测试”的坏习惯。更好的循环是：

```text
写一个失败测试
确认它真的失败
写最少代码让它通过
跑测试
必要时重构
继续下一个行为
```

这要求代码库本身有清楚的测试边界。如果代码库是很多浅模块拼在一起，Agent 会很难判断应该测哪里。深模块更适合 Agent：接口小、内部逻辑集中、测试边界明确。

## 第八步：人工 QA，把品味压回系统

AFK 实现结束后，Matt 会让 AI 根据最近几次提交生成一份 QA plan，然后自己手动走一遍。

这个阶段经常会发现规格里没想到的问题：

- 按钮文案暴露了内部术语，比如 ghost course
- 创建成功后没有跳转，用户不知道发生了什么
- 按钮没有 loading state，看起来像没响应
- 删除真实 lesson 时缺少确认弹窗
- 文件系统写入失败后，数据库和磁盘状态不一致

这些问题不一定是 Agent “写错了”，很多是早期讨论没覆盖到。QA 的作用就是把真实体验带回来。

Matt 的做法是把 QA 中发现的问题直接变成新的 issue，再交给 Ralph loop 或类似 AFK agent 去修。这样人可以一边继续 QA，一边让 Agent 在后台修上一批问题。

## 第九步：代码审查时看输入和输出

Matt 不会逐行审每一段 AI 写出的实现。他更关注几个东西：

- 这个模块的接口有没有变得清楚
- 测试是否覆盖了真正的行为
- 用户路径是否符合预期
- 错误状态和边界条件是否处理
- 代码是否破坏了已有架构形状

这不是说代码不重要，而是审查重心发生了变化。人更像在审系统形状和行为契约，而不是亲自盯每个 if 分支。

## 第十步：持续整理架构，让 Agent 更容易成功

Matt 反复提到一个观点：坏代码库会放大 Agent 的坏输出。

如果代码库里到处是小而浅的模块，依赖关系散乱，测试边界模糊，Agent 每次都要花大量上下文理解“到底谁负责什么”。这种情况下，提示词再好也有限。

更适合 Agent 的代码库通常有几个特征：

- 模块接口小，内部能力集中
- 业务概念有稳定命名
- 测试能覆盖完整行为，而不是只测零碎函数
- 关键服务有清楚的输入输出
- 架构规则可以被 skill 或文档按需拉取

人应该设计模块接口，把模块内部实现交给 Agent。这样既能保持对代码库的整体掌控，又不会被细节淹没。

## 可以直接套用的工作清单

### HITL 阶段

- [ ] 写下原始想法，至少说明 what 和 why
- [ ] 让 AI Grill Me，一次只问一个问题
- [ ] 对关键领域词建立统一定义
- [ ] 明确 out of scope
- [ ] 生成 PRD
- [ ] 把 PRD 拆成垂直切片 issue
- [ ] 审查 issue 是否太大、太小或太水平
- [ ] 标出哪些任务是 AFK，哪些必须 HITL

### AFK 阶段

- [ ] Agent 只领取未阻塞的 AFK issue
- [ ] 每个 issue 都有验收标准
- [ ] 优先使用 TDD
- [ ] 每次提交前跑测试、类型检查、lint
- [ ] 自动 review 最近提交
- [ ] 完成后留下清楚的提交信息或 issue 评论

### QA 阶段

- [ ] 让 AI 根据提交生成 QA plan
- [ ] 人按真实用户路径手动 QA
- [ ] 把问题写成新的 issue
- [ ] 继续让 AFK loop 修复明确问题
- [ ] 对最终结果做人工 code review

## 实践时最容易踩的坑

**把 HITL 伪装成 AFK**，比如让 Agent 自己决定产品规则、UI 文案、架构边界。这样做看起来自动化程度高，最后会把判断债留给 QA。

**把任务拆成水平层**，比如数据库一个 issue、API 一个 issue、前端一个 issue。这样的 issue 很难独立验收，也会让反馈推迟。

**缺少反馈闭环**，没有测试、类型检查和可运行环境时，Agent 只能猜。猜出来的代码越多，后面人要付的审查成本越高。

**长期保留过期文档**，旧 PRD、旧设计说明和旧计划如果没有生命周期，会误导后续 Agent。能关闭的关闭，能归档的归档，当前事实以代码、测试和活跃 issue 为准。

**完全跳过人工 QA**，自动测试能证明很多事，但证明不了体验顺不顺、术语是否别扭、交互是否符合预期。AI 可以帮你写 QA plan，但不能替你拥有品味。

## 我的理解

这套工作流真正有价值的地方，不是某个工具或脚本，而是重新划清了人和 Agent 的边界。

人不应该把自己降级成“提示词输入员”，也不应该幻想 Agent 能独立完成所有判断。更合理的位置是：人负责定义问题、切任务、设计边界、校验结果；Agent 负责在这些边界内快速执行。

如果用一句话概括：**HITL 负责让事情做对，AFK 负责把事情做完。**
