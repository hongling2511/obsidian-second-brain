## 一句话总结

**这套方法不是让一个最强 Agent 从头做到尾，而是让人只与一个协调 Agent 对话，由它把研究、原型、前后端实现和验证拆成可并行的工作流；人把精力集中在需求、取舍、体验、权限和最终证据门槛上。**

## 核心框架：一个联络点，多个执行面，若干人工关口

```text
口述模糊想法
  ↓
协调 Agent 整理上下文
  ├─ 市场研究
  ├─ 技术研究
  └─ 竞品启发
  ↓
交互式方案评审（成本、范围、架构、体验）
  ↓
可点击低保真原型 → 人工体验反馈 → PRD
  ↓
设计系统、前端、后端、基础设施并行实现
  ↓
本地质量门禁 + Agent 自测
  ↓
真实端到端验收
```

这可概括为 **1-3-4 模型**：

- **1 个联络点**：人只对 Firstmate 说目标、反馈和新想法，不亲自协调每个执行 Agent。
- **3 类工作并行**：产品发现、技术决策、体验原型不是串行等待，而是同时推进、相互校正。
- **4 个人工关口**：产品是否值得做、方案取舍、用户体验、最终可验证结果。

Firstmate 官方仓库对这一模式的定义是：一个 liaison 负责派发、监督和升级真正需要人的决定；每个 crewmate 在可见会话和隔离 worktree 中工作，最后交付 PR、合并结果或研究报告。这里的关键不是“多 Agent”本身，而是**把协调成本封装进一个持续存在的负责人**。[来源：Firstmate 官方 README](https://github.com/kunchenguid/firstmate)

## 方法拆解

### 1. 先高带宽倾倒上下文，不急着写规格

讲者从空仓库开始，用一段约 3,000 字符的口述交代：

- 真实问题：家庭靠纸笔和记忆管理孩子零花钱；
- 用户与角色：家长可操作，孩子只读；
- 产品价值：顺带教授余额、借贷、还款和利息；
- 边界：只记录虚拟金额，不移动真钱；
- 平台与数据要求：先做 iOS，多个设备之间需要云端同步。

重点不是 prompt 写得工整，而是把**动机、约束、例外和未决问题**一次性暴露给协调 Agent，再让它结构化。[06:00–10:00](https://www.youtube.com/watch?v=kPN564Kol14&t=360s)

这与 [[AI Agent开发工作流实践：AFK与HITL]] 的思想相通：人先提供“为什么”和判断边界，Agent 才能把后续工作拆成可执行任务。

### 2. 研究不是写报告，而是为决策减少不确定性

协调 Agent 同时派出：

- 市场研究：是否已有满足完整约束的产品；
- 技术研究：原生客户端、认证、数据模型、云端持久化如何组合；
- 后续竞品分析：从相邻产品提炼只读儿童视图、活动时间线、情境式金融教育、零花钱规则等可借鉴机制。

市场研究回答“要不要做”，技术研究回答“怎么做”，竞品研究回答“什么值得吸收”。三者输出必须回到具体决策，而不是停在长篇 Markdown 报告。[10:00–20:00](https://www.youtube.com/watch?v=kPN564Kol14&t=600s)、[24:00–29:00](https://www.youtube.com/watch?v=kPN564Kol14&t=1440s)

### 3. 把文本墙变成可操作的决策界面

技术报告长达 351 行，讲者没有逐行阅读，而是要求 Agent 把关键取舍做成 Lavish HTML artifact：

- 托管 Supabase 与低价 VPS 的成本、运维和扩展性对比；
- 身份体系、权限边界与数据流图；
- 需要人拍板的开放问题；
- 可直接在界面中标注、删除和反馈的方案元素。

第一次方案基于错误的 VPS 成本估算而偏向 Supabase。讲者指出错误后，Agent 重新查价并改为低成本 VPS。这说明交互式计划的价值不只是“更好看”，而是让**假设、数字和隐藏需求可被定位、质疑和修改**。[30:00–42:00](https://www.youtube.com/watch?v=kPN564Kol14&t=1800s)

Lavish 官方说明支持对本地 HTML 的元素、文字和 Mermaid 图进行标注，并把反馈送回 Agent；其定位正是补齐 HTML artifact 的人机协作回路。[来源：Lavish 官方 README](https://github.com/kunchenguid/lavish-axi)

### 4. 先做可点击的低保真原型，再冻结 PRD

Agent 最初只产出原型范围文档，讲者进一步要求做真正可点击的 HTML wireframe。他实际走完家长建家庭、设备配对、孩子只读视图、家长 PIN、零花钱、贷款和课程路径，并现场纠正：

- 使用当地真实货币单位，而不是抽象 token；
- 删除重复入口；
- 孩子不在应用内请求金额，而是线下和家长沟通；
- 教学采用短而线性的路径；
- 此时只验证信息架构和流程，不追求视觉精致。

反馈完成后才让 Agent 把已决事项沉淀为 PRD。[42:00–48:00](https://www.youtube.com/watch?v=kPN564Kol14&t=2520s)

这里的顺序是：

> **研究给候选方向 → 可点击原型暴露体验问题 → 人做选择 → PRD 记录已达成的共识。**

### 5. 按“依赖关系”并行，而不是机械地多开 Agent

当 PRD 和方向足够稳定后，工作被分成多个可并行轨道：

- 设计系统与视觉探索；
- 原生 SwiftUI 前端；
- 后端 API 与数据库；
- VPS、DNS、HTTPS、备份和基础设施即代码；
- Apple Developer 配置；
- 后续集成与缺陷修复。

协调 Agent负责把人的新反馈路由到正确轨道。例如基础设施实现过程中，讲者提出改用 OpenTofu，Firstmate把方向传给对应 worker；端到端测试同时发现文案问题时，又开独立任务修正，而不打断主测试。[59:41–01:16:00](https://www.youtube.com/watch?v=kPN564Kol14&t=3581s)、[01:29:00–01:34:00](https://www.youtube.com/watch?v=kPN564Kol14&t=5340s)

适合并行的前提是：

- 输出边界明确；
- 共享接口或依赖已定义；
- 每条轨道有独立验证方式；
- 有单一协调者持续处理状态和冲突。

Herdr 官方把自己定义为面向 Agent 的 terminal multiplexer，可查看 Agent 是 working、blocked 还是 done，并允许会话持续运行和重新连接；它解决的是**执行可见性与会话生命周期**，而 Firstmate解决的是**任务分派与监督**。[来源：Herdr 官方仓库](https://github.com/ogulcancelik/herdr)、[Agent 文档](https://herdr.dev/docs/agents/)

### 6. 人不盯工具调用，但必须盯判断、权限和证据

讲者启用 calm mode 隐藏工具调用噪声，只看请求、结果和进度；这降低了注意力消耗，却不意味着完全放任。视频中人多次介入：

- 否决基于错误成本的 Supabase 建议；
- 删除 MVP 阶段不必要的审计、导出和多环境设计；
- 判断视觉设计“不像儿童应用”；
- 为生产密钥的每次使用逐项授权；
- 要求 Agent 不要把只有自己能做的工作甩回给人；
- 在完成汇报后追问：前端是否真的连接真实后端？

因此，更准确的分工是：

| 人负责 | Agent 负责 |
|---|---|
| 目标、范围、品味、成本容忍度 | 探索、拆解、实现、修复 |
| 高风险权限与生产变更授权 | 准备操作并说明所需权限 |
| 识别过度工程与错误假设 | 根据反馈重新研究和调整 |
| 定义完成证据 | 执行测试并收集证据 |

### 7. “完成”必须由用户路径定义，不由提交数量定义

前后端 PR 合并后，协调 Agent一度报告工作基本完成。讲者追问后发现客户端仍使用 mock，并未连接后端，于是把 MVP 的 Definition of Done 改成：

> 在 iOS Simulator 中使用真实 Apple 账户登录，连接真实 HTTPS 后端；写入金额后，退出再登录仍能从云端读取同一数据。

这个终点倒逼 Agent 重新识别前后端集成、DNS、认证、配置和错误修复等缺口。[01:20:33–01:24:00](https://www.youtube.com/watch?v=kPN564Kol14&t=4833s)

No Mistakes 作为更强质量门禁，官方流程是在隔离 worktree 中依次执行 review、test、docs、lint、push、PR 和 CI，全部通过才推送；讲者在视频中则刻意把它延后到 MVP 有实质代码、原本会需要同行审查的阶段。[来源：No Mistakes 官方 README](https://github.com/kunchenguid/no-mistakes)、[52:00–54:00](https://www.youtube.com/watch?v=kPN564Kol14&t=3120s)

## 贯穿案例：Eddie's Wallet

这场演示从空目录推进到一个“儿童虚拟钱包”：

1. 用家庭真实痛点定义产品，不先列功能。
2. 市场调研确认没有完全匹配的替代品。
3. 技术调研提出原生 SwiftUI、云端账本和认证方案。
4. 人通过成本和范围评审，从托管服务改选低价 VPS。
5. 用可点击 wireframe 验证家长/儿童模式和核心流程。
6. 把反馈写入 PRD，再创建 GitHub 仓库。
7. 设计系统、前端、后端和基础设施并行构建。
8. 用模拟器中的真实登录、写入、重新登录和云端读取作为端到端门槛。

公开仓库可确认项目定位是 iPhone/iPad 的 SwiftUI 虚拟零花钱应用，孩子侧只读，所有金额均为不可兑换的模拟数据。[来源：Eddie's Wallet 官方仓库](https://github.com/kunchenguid/eddies-wallet)

## 适用场景

这套方法更适合：

- 从模糊想法到 MVP 的探索型项目；
- 前端、后端、基础设施、研究可形成独立轨道的全栈任务；
- 有成熟测试、版本控制和隔离工作区的工程环境；
- 操作者有能力判断架构、成本、产品体验和风险；
- 等待成本高于 Agent 调用成本，希望压缩项目日历时间。

不太适合：

- 需求和接口都高度耦合，拆分后频繁互相阻塞；
- 缺少自动测试、构建和可观察反馈；
- 团队无法承担多个 Agent 的成本与并发冲突；
- 高合规、高安全项目却没有严格审批、审计和密钥隔离；
- 使用者无法判断 Agent 的错误假设和过度工程。

## 前提与局限

### 前提

- 代码库必须给 Agent 提供可执行反馈：测试、lint、构建、UI 或 API 证据。
- 任务需要隔离工作区，否则并行 Agent 会互相覆盖。
- 关键状态要持久化；长会话的上下文压缩不能成为唯一记忆。
- 生产权限应按动作授权，密钥不能作为普通文本散落在上下文和仓库。
- 人必须能识别产品、架构与安全上的“不对劲”。

### 局限与需谨慎看待的主张

1. **这是单次演示，不是受控实验。** 它证明这套组合在讲者的设备、账号、预置工具和经验下可以工作，不能证明同样的时间、成本或成功率可普遍复现。
2. **环境并非真正“从零”。** 仓库为空，但 Herdr、Firstmate、Pi、Lavish、浏览器远程控制、密钥库、GitHub、Apple Developer、Cloudflare、VPS 账号和域名都已配置。
3. **并行会放大协调错误。** 视频中前端因并行开发指向错误后端地址，说明接口和运行配置仍需集中管理。
4. **隐藏工具调用会降低早期纠错机会。** calm mode 适用于可靠模型和成熟门禁，不应被理解为“无需监督”。
5. **自动压缩“无明显损失”只是讲者观察。** 视频经历多次 compaction 后仍能继续，但未给出系统化准确率评估。
6. **最关键的核验存在公开资料冲突。** 视频结尾展示并口述“真实 Apple 登录 + 生产后端 + 云端持久化”已端到端工作；但同日公开仓库 README 明确写着，实时 Apple 登录和完整生产流程“尚未端到端验证”。仓库的 [video claims checklist](https://github.com/kunchenguid/eddies-wallet/blob/main/docs/video-claims-checklist.md) 甚至把“不得声称已完成真实端到端验证”列为硬性要求。因此，视频中的成功画面应视为**演示主张**，而不是已经由公开仓库复现的工程证据。

## 最值得迁移的实践

> [!quote] 我的理解
> 高效的 Agentic Engineering 不是把人从工程中移除，而是把人从“逐行操作与会话搬运”提升到“定义问题、纠正假设、授予权限、判断体验和要求证据”。

- [ ] 为新项目先录一段 5–10 分钟语音，覆盖问题、用户、动机、边界和未知项。
- [ ] 同时启动市场、技术和体验三类探索，但要求每份研究绑定一个待决问题。
- [ ] 把超过一屏的方案改造成表格、流程图或可交互原型。
- [ ] 在 PRD 前做一次可点击低保真原型评审。
- [ ] 给每条并行轨道写清输入、输出、依赖和验证命令。
- [ ] 把“完成”写成可观察的真实用户路径，而不是“代码已合并”。
- [ ] 对生产密钥、付费资源、DNS 和外部发布保留逐项人工授权。
- [ ] 把公开视频或现场演示的主张，与仓库中可复现的测试证据分开记录。

## 是否值得看完整视频

**值得选择性观看，不必逐分钟看完。** 信息密度最高的是需求输入、交互式规划、原型反馈和端到端门槛四段；大量等待、界面操作和工具展示可倍速跳过。真正有迁移价值的不是讲者使用了哪些具体工具，而是这条原则：

> **让 Agent 承担并行执行与状态搬运，让人持续掌握决策权、生产权限和完成定义。**
