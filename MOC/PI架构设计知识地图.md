# PI 架构设计知识地图

> 本页是 [[pi的设计艺术]] 一书的知识导航枢纽，串联书籍笔记与提炼出的核心思维模型。

## 核心主线

> **如何用尽可能薄的内核，撑起尽可能丰富的产品？**

pi 的回答是一套"洋葱架构"：统一 LLM 抽象 → 无状态循环引擎 → 有状态运行时 → 产品壳。每一层只知道下一层的接口，不知道上层的存在。

## 核心思维模型

这些概念从 pi 的设计中提炼，可复用于其他系统设计：

| 思维模型 | 一句话定义 | 对应章节 |
|---------|----------|---------|
| [[洋葱架构]] | 系统按同心圆分层，依赖只向内，外层对内层完全无知 | Ch 1-2 |
| [[Agent循环引擎]] | 无状态纯函数实现的 LLM 调用→工具执行→再调用循环 | Ch 8-10 |
| [[插件注册表模式]] | 98行代码实现运行时无限扩展的注册/查找机制 | Ch 4, 15, 18 |

## 关键设计模式速查

| 模式 | 出现位置 | 核心思想 |
|------|---------|---------|
| 插件注册 | api-registry.ts | register/get/unregister，98行 |
| 有损变换 | transform-messages.ts | 跨模型消息归一化 |
| 流式契约 | StreamFn type | "Must not throw" |
| 双层循环 | agent-loop.ts | 内层忙碌，外层等待 |
| 三阶段执行 | prepare/execute/finalize | 工具执行管道 |
| 声明合并 | CustomAgentMessages | 类型安全的扩展点 |
| Append-only 树 | session-manager.ts | JSONL + parentId |
| Pluggable I/O | EditOperations/BashOperations | 可插拔后端 |
| 极简组件 | Component { render() } | string[] 返回值 |

## 反主流决策一览

| 不做 | 替代方案 | 核心回调 |
|------|---------|---------|
| 不内建 Sub-agents | tool call + Agent 循环嵌套 | `AgentTool.execute()` |
| 不内建 MCP | Skill (markdown) + Extension (代码) | system prompt + `registerTool()` |
| 不内建 Permission popup | 权限钩子 | `beforeToolCall()` |
| 不内建 Plan mode | 上下文变换 | `transformContext()` |

## 数字速览

- **总代码量**：~120,000 行 TypeScript
- **核心抽象**：~3,000 行（驱动 100% 产品形态）
- **内核占比**：24%（pi-ai + pi-agent-core）
- **Provider Registry**：98 行
- **Agent Loop**：~70 行核心逻辑
- **产品形态**：4 种（CLI、Slack、Web、RPC）
- **内建 Provider**：10 种 API 协议，23 家厂商
- **版本基线**：pi-mono v0.66.0（2026年4月）

## 适用场景评估

> 在考虑是否借鉴 pi 架构时，问自己这几个问题：

- [ ] 是否需要支持 2-3 种以上产品形态？
- [ ] 是否需要支持 2-3 家以上 LLM Provider？
- [ ] 团队是否有能力阅读和理解分层源码？
- [ ] 是否需要不同产品有不同的安全模型？
- [ ] 迭代速度和定制深度哪个更重要？
