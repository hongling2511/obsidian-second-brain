# Agent Runner 产品规划

> **把明确的开发任务交给自己的机器，在人不在线时执行；最终交付带验证证据的 Draft PR，或清楚、可接续的阻塞报告。**

版本：v0.2 规划草案。基于 [[构建基于 vps 的开发工作流]]，于 2026-09-22 核对相关官方资料，并按用户提供的 OpenAI Symphony 项目补充设计借鉴。本文中的技术选型、指标和商业实验均为建议，未视为用户已批准实施。按验收里程碑推进，暂不承诺日历截止日期。

## 项目概述

### 1. 已有共识与本轮建议

| 决策性质 | 内容 |
| --- | --- |
| 原讨论明确的目标 | 使用现成编码 Agent，在人不在线时自主领取任务、修改代码和交付结果。 |
| 原讨论明确的设备选择 | 先利用闲置 MacBook，之后根据实际需求考虑 VPS。 |
| 沿用原草案的工作基线 | GitHub Issue 输入、人工审核 PR、单任务并发、持久化状态、有限重试、避免接触生产环境。 |
| 本轮推荐的实现 | Python 单进程调度器、SQLite、Docker worker、容器内独立 Git clone；借鉴 Symphony 编排规范，首个适配器使用 Codex App Server。 |
| 本轮新增的产品要求 | 可信的验证证据、发布防重、取消与恢复、预算可见、项目接入诊断、明确的主机可用性边界。 |

**“人不在线”不等于机器断网。** 主机仍需联网访问代码托管与模型服务。本产品的第一目标是减少盯终端和处理重复操作的时间，而不是保证任意需求都能自动完成。

### 2. 产品定位、用户与任务范围

首个用户就是自己。外部验证对象是已经使用编码 CLI、维护少量 Git 仓库、愿意审核代码的独立开发者。先验证同一类用户的问题，再考虑小团队。

用户的核心诉求是：“我能写清楚一项开发任务，但不想一直守着 Agent 安装依赖、运行测试、处理超时和整理 PR。”

适合首版的任务包括：有复现步骤的小缺陷、明确接口下的小功能、补充回归测试、局部重构和文档修订。每项任务应有可判断的验收条件，并能在一个仓库内完成。

首版不承接需求开放的整站开发、跨仓库改造、生产故障处置、数据库迁移执行、涉及真实客户数据的调试。运行配置首先覆盖可在 Linux 容器中验证的项目；Xcode、iOS/macOS 原生构建不属于这一配置。

产品责任分为三层：

| 层次 | 应负责的结果 |
| --- | --- |
| 人 | 提供目标与验收条件，授权任务，审核并决定是否合并。 |
| Runner | 调度、执行边界、验证、状态恢复、费用记录、提交与 PR 发布。 |
| 编码 Agent | 理解代码、修改文件、根据验证失败信息尝试修复、说明变更。 |

Runner 不自建模型推理、通用 Agent 循环或新的代码编辑器。它的价值应体现在“任务能可靠交接”，而不是支持多少个模型名称。

### 3. 现有方案与构建判断

原讨论中“目前没有满足条件的开源方案”不能继续作为产品立项依据。本次核对到以下直接相关方案：

| 方案 | 官方资料中可确认的能力 | 对本项目的启示 |
| --- | --- | --- |
| OpenAI Symphony | 提供编排规范和 Elixir 参考实现；当前实现已包含 GitHub Issues 适配器，并通过 Codex App Server 执行任务，定位仍为工程预览。[^symphony][^symphony-implementation] | 将其作为编排参考基线；GitHub 接入本身不能再作为差异化理由，具体取舍见第 21 节。 |
| Vibe Kanban | 已有任务看板、Agent 工作区、代码审阅和多 Agent 接入；当前官方 README 明确显示项目正在 sunset。[^vibe] | 多 CLI 加看板本身不是独特卖点；维护状态应计入依赖选择。 |
| OpenHands | 当前仓库介绍 Agent Canvas、Agent Server，以及调度和事件自动化相关组件。[^openhands] | 自托管和自动化也不是独占能力，应避免单纯复制完整工作台。 |

**推荐方向：先做个人自托管的轻量任务交付服务。** 以 Symphony 的语言无关规范为编排参考，沿用 Python 单进程方案，把实现投入集中在可信交付、持久化恢复和安装诊断上。选择 Python 是因为本版主要处理进程、文件、HTTP 和持久化，不需要前端或复杂 Agent 框架。采用的是经过裁剪的设计，不声称实现完整 Symphony 兼容协议。

最小替代方案是直接配置 Symphony 完成自用。如果自用验证表明它已经以更低维护成本满足这里的验收要求，应停止开发重复内核，改为做接入配置或分发支持。**这是明确的停止条件，不能为了拥有一个新产品而继续增加功能。**

现阶段对差异化的判断是待验证假设：用户可能愿意为更容易安装、更少人工接管和更可信的交付记录付费。尚无用户访谈、付费或对比实测证据支持这一判断。

### 4. 成功标准

先登记一组 20 个真实、范围清晰的任务，保留失败任务，不在结果出来后更换样本。以下是产品验证目标，不是已经达到的能力或对模型效果的保证。

| 指标 | 定义与初始目标 |
| --- | --- |
| 无人接管的可审查交付率 | 20 个预登记任务中，至少 60% 不需人工进入执行环境修改代码，便能形成符合约定检查的 Draft PR。 |
| 实际采用率 | 独立记录最终合并、放弃和人工重写比例；不能把“创建了 PR”当作用户已接受成果。 |
| 人工投入 | 记录接入、补充需求、接管、审阅、维护的时间，与直接使用 CLI 的同类任务基线比较；以总投入下降作为继续开发依据。 |
| 可靠性 | 验收场景中重复发布 PR 为 0、错误报告检查通过为 0、取消后违规继续发布为 0。 |
| 可解释性 | 每个终止任务都有原因、已保留的产物位置以及下一步操作；费用无法取得时明确显示未知。 |

## 项目计划

### 5. 用户工作流与首版界面

```text
接入一个仓库并验证环境
          ↓
用户填写 Issue，授权进入 agent:ready
          ↓
Runner 固化任务、代码基线和执行配置
          ↓
准备隔离环境 → Agent 修改 → 独立验证
          ↓
通过：发布 Draft PR      未通过：有限修复或阻塞报告
          ↓
用户在 GitHub 审阅、决定合并；Runner 记录结果
```

**GitHub 就是首版的任务和审阅界面，CLI 负责机器运维。** 用户能从 Issue 的状态评论看到当前阶段、最近进展时间、运行编号和 PR 链接。每个任务维护一条带稳定标记的状态评论，回传结果不确定时先查找再更新；只在阶段变化、需要介入或结果产生时更新，不逐条转发模型输出。

任务输入包含四项：目标、验收条件、允许修改的范围、必要的复现步骤或样例。仓库、基线分支、检查命令和执行预算来自已登记的项目配置，不能由 Issue 正文临时改写。

首版只读取 Issue 标题与正文作为任务输入。普通评论不自动变成指令。缺少验收条件时进入 `blocked:needs_input`，列出具体缺项，停止计费执行。用户补齐后通过明确的重新入队操作生成新修订。

Issue 标签用于呈现：`agent:ready`、`agent:running`、`agent:review`、`agent:blocked`、`agent:failed`、`agent:hold`、`agent:done`。其中 `agent:done` 仅用于关联 PR 已合并的结果。标签操作不是并发锁；本地任务账本才是执行状态的权威来源。[^labels]

**入队授权**：只接入显式登记的私有仓库，只接受白名单内、具备仓库写权限的任务作者和授权者；自动入口还要核验添加 ready 标签的操作者。公开仓库中陌生人提交的任务不进入首版无人值守范围。

同一个 Issue 反复加 ready 标签不会自动产生新执行。失败后的重试、需求修改后的重新执行，都要成为有记录的显式操作。Issue 关闭或加 `agent:hold` 后停止待执行及活跃任务；外部操作的生效延迟受轮询周期限制。

`agent:ready` 仅作为入队条件；Runner 开始后将其替换成 `agent:running`，不会因此取消已授权任务。不能直接照搬 Symphony 的“运行中仍必须包含 required_labels”规则，否则状态展示会误触发取消。已入队任务的停止条件是持久化取消、Issue 关闭、hold 或授权失效；`review_ready` 与 `blocked` 即使对应 Issue 仍开放，也不自动重启编码。[^symphony]

轮询及发布前重新读取标题和正文，与任务快照摘要比较；发生变化时阻塞当前修订，由用户明确授权 `revise`。只变化标签或机器人状态评论不应触发需求漂移。关联 PR 的合并与关闭状态单独回读，不能仅根据 Issue 已关闭推断任务是否成功。

### 6. 交付物的定义

Draft PR 应包含：关联 Issue、任务修订、基线 SHA、实际提交 SHA、变更摘要、逐项验收结果、检查命令与退出状态、修复轮次、执行环境和 Agent 版本、费用记录类型、尚待人工检查的风险。

PR 正文中的“测试通过”必须来自 Runner 执行的验证记录。Agent 的总结可以作为说明文字，但不能改变检查状态。全文日志默认留在执行机，只向 GitHub 发布脱敏摘要。

三类结果必须明确区分：

| 结果 | 判定 |
| --- | --- |
| `review_ready` | 固定代码快照通过约定门禁，分支已推送，Draft PR 已创建或找回，并完成远端回读。 |
| `blocked` / `failed` | 缺少输入、权限、可用环境，触及政策边界，或在预算内未能通过检查。保留可检查的证据。 |
| `no_change` | 没有代码变更；附上检查结果和理由，不创建空 PR，也不计作一次成功的代码交付。 |

本地检查通过不等于远端 CI 已通过。首版在 PR 中明确区分“本地通过”和“远端状态尚未确认”；合并仍由人按仓库规则决定。GitHub 的 Draft PR 是已有发布能力。[^pulls]

### 7. 范围与版本

| 版本 | 提供的完整能力 | 进入下一阶段的条件 |
| --- | --- | --- |
| P1：单任务交付 | CLI 提交任务；单仓库、单 Codex、容器执行、固定检查、预算和取消、状态持久化、恢复、Draft PR。 | 人工触发时完整交付可用，发布和验证的故障用例通过。 |
| P2：无人值守 MVP | 加入 Issue 自动领取、授权校验、launchd、重启协调、标签与评论回传、留存清理。 | 在目标闲置 MacBook 上通过完整验收矩阵，并完成 20 个真实任务评估。 |
| P3：个人产品版 | 安装与升级流程；接入第二种 CLI；支持经明确授权的 PR 反馈修订和原 PR 更新。 | 外部试用证明无需作者反复代配置，升级和兼容性可维护。 |
| P4：扩大使用范围 | Linux 单机部署、多项目配额；有证据需要时再增加只读 Web 状态页。 | 个人版有持续使用，支持成本可承受。 |

P1 本身是可用的 CLI 产品；P2 本身是完整的无人值守服务；后续阶段可以停止而不影响前一阶段使用。

多机控制平面、团队权限与计费、多 Agent 相互派工、自动合并、生产部署、聊天入口、浏览器桌面控制、长期知识记忆都不在 MVP。需要 Xcode 的宿主机执行配置单独评估，不能作为 Linux worker 的透明降级。

### 8. 技术架构

```text
GitHub Issues / CLI
         │
         ▼
MacBook：Runner 控制进程（专用 macOS 用户）
  ├─ 已批准的 WORKFLOW.md + 宿主配置 + 任务账本 ── SQLite
  ├─ 先协调再派发 / 恢复 / 取消 / 事件记录
  ├─ 工作区与 Docker 生命周期
  │        └─ 临时 worker：独立 clone + Codex App Server → 模型服务
  ├─ 独立 verifier：固定快照 + 已批准的检查命令
  └─ 发布器：干净 Git 检出 + 托管平台凭据 → 分支 / Draft PR
```

只有一个新的常驻业务进程。调度、执行管理、验证和发布是进程内模块；worker 和 verifier 是由它管理的临时容器。SQLite 保存状态与待回传操作，不引入 Redis、消息中间件或独立 API 服务。完整实现会超过 8 个源代码、测试和配置文件，应按一个小型服务而非几条 shell 命令管理。

**工作区选择修正：MVP 使用每任务独立 clone。** Git worktree 会共享部分仓库元数据，它适合节省空间，但本身不构成安全沙箱。[^worktree] 容器执行时，独立 clone 能避免共享 `.git` 路径映射和写权限问题。先承担额外磁盘与拉取成本；确有瓶颈后再加入受控缓存或 worktree 优化。

worker 只挂载本任务目录和必要的临时存储，不挂载整个用户目录、Runner 状态目录、发布器凭据或 Docker socket。模型 CLI 与项目命令在 worker 内运行；创建容器的权限仅属于受信任的 Runner。Docker 官方文档明确提醒，能够控制 daemon 的用户具备很强的宿主机访问能力。[^docker-security]

工作区身份绑定“项目 ID + Task ID + 修订号”。同一修订的修复从已保留变更继续，新修订使用自己的 clone；每次 Run 的编码容器仍为临时容器。按创建、执行前、执行后、清理前划分生命周期，但不开放仓库脚本在宿主机上任意执行的 hooks；项目准备命令在受限容器内运行。清理必须遵守第 16 节的证据留存规则。

### 9. Agent 接口与选型

参考 Symphony，首个适配器改为通过 stdio 调用容器内的 `codex app-server`，使用结构化会话、执行事件和中断接口。App Server 是 Codex 自带的程序化接口；此处为每个 Run 启动的临时子进程，不新增公开网络服务。`codex exec --json` 仍适合手工单次烟雾测试，但首版产品不同时维护两套 Codex 运行后端。[^codex-app-server][^codex]

| 适配器 | 接入方式 | 排期 |
| --- | --- | --- |
| Codex | App Server stdio；显式 thread/turn、事件解析、输入或审批需求、中断与用量归属。 | 首版，替代 v0.1 的 exec 产品适配器。 |
| Claude Code | `-p` 非交互与 `stream-json` 输出。[^claude] | P3 的第二适配器候选。 |
| Pi | RPC 模式提供结构化交互、终止与状态读取。[^pi] | 用户的真实模型或工作流需要它时接入。 |

统一的是运行契约：启动、结构化事件、终止、错误分类、用量、会话标识和可用能力。**不强制三种 CLI 的底层模型调用统一成同一种 API 格式。**

适配器需声明是否支持续接、精确终止、用量报告和特定鉴权方式。费用或续接不受支持时，明确降级，不伪造数值，不使用其他任务的“最后一次会话”。每次记录 CLI 版本；升级先运行契约测试，再替换固定 worker 镜像。

接入顺序固定为连接初始化、`thread/start`、`turn/start`、读取事件与终态。记录 `thread_id`、`turn_id` 和请求关联 ID；收到输入或审批需求时写入阻塞原因并结束资源占用，不自动代替用户回答。取消时先向当前 Run 的准确 thread/turn 请求 `turn/interrupt`，确认终态；超过停止窗口仍未退出时，按容器终止规则处理。中断请求的确认响应不等于任务已停止。[^codex-app-server]

首版每个 Run 只启动一个编码 turn；turn 正常完成后停止编码容器，进入独立验证；失败、中断或输入需求按第 12 节分类处理。验证失败才以新的 Run、代码快照和失败反馈执行有限修复，不因 GitHub Issue 仍为 open 而连续追加 turn。模型内部工具调用不计作新的 Run；新的 `turn/start` 则必须先占用任务累计编码次数。恢复不依赖跨版本的模型内部会话，后续需要对话续接时再扩展能力。

### 10. 任务模型、状态与发布防重

区分 **Task（用户意图及其修订）**、**Run（一次执行尝试）**、**Artifact（变更和证据）**。一次 Task 可以对应多个 Run，但不能因为重试重复创建同一修订的 PR。

| 持久化对象 | 必需字段 |
| --- | --- |
| Project | 仓库稳定 ID、remote、基线分支、允许的操作者、执行镜像、检查命令、路径政策、配置摘要、凭据引用。 |
| Task | 来源 ID、修订号、标题正文快照与摘要、基线 SHA、状态、取消标记、累计调用次数、执行截止时刻、发布截止时刻、目标分支、PR 标识。 |
| Run | Task ID、尝试序号、Agent 与版本、镜像摘要、容器 ID、thread/turn ID、开始/结束/Runner 心跳/最后有效 Agent 事件、用量、错误分类。 |
| Artifact / Check | 不可变代码快照摘要、patch/文件清单、候选提交 SHA 与 Git bundle 位置、各检查记录、日志位置、留存状态。 |
| Outbox | 外部操作类型、稳定操作键、目标分支或 PR、重试时间、外部返回 ID、最近错误。 |

自动入口的 Task 唯一键为“仓库稳定 ID + Issue 编号 + 显式修订号”。CLI 输入使用持久化的请求 ID。重复轮询或普通 Issue 编辑不会隐式递增修订。

正常执行状态为 `queued → preparing → executing → verifying → publishing → review_ready`。补充状态为 `retry_wait`、`blocked`、`failed`、`cancelled`、`no_change`；关联 PR 合并后记录 `merged`，未合并关闭则记录 `closed_unmerged`。两种关闭结果不能混为任务成功。

用单实例进程锁、SQLite 事务和唯一约束完成本机领取。状态转换与对应 Outbox 意图在同一事务内写入。SQLite 支持的写事务机制适合这里的单机写入场景。[^sqlite] 本方案不声称同一个 Issue 能由多台独立 Runner 安全竞争，首版禁止这种部署方式。

发布器采用稳定分支名 `agent/issue-编号-r修订号`，CLI 来源使用 Task ID。发布前按仓库、head 分支、base 分支和任务标记查询既有 PR；创建请求超时或返回冲突时先查询，不直接再创建。推送结果不确定时先核对远端分支 SHA。只推送 Runner 生成的任务分支，拒绝主分支、其他用户分支和强制推送。

向远端推送前，先生成候选提交并持久化其 SHA、包含该提交对象的 Git bundle 和 Outbox 意图。发布重试复用同一提交对象，不能因为重新生成提交时间戳而得到不同 SHA。恢复执行前同时检查调用余额、执行期限和取消标记，余额用尽或已到期时不得启动新的 Agent。

网络调用与数据库提交不能组成一个跨系统原子事务。这里的目标是“允许重试执行，外部效果可协调并去重”，不是宣称所有步骤恰好执行一次。远端分支或 PR 被人工改动、删除，或者查询结果无法消除歧义时，进入阻塞状态，不自行覆盖。

重新启动时先恢复协调，再领取新任务：检查有标记的容器、持久化阶段和远端发布结果。对于遗留的执行或验证容器，先停止并确认退出，再从保留快照创建新的 Run；对于已验证但发布中断的任务，只恢复发布。不能仅凭 PID 判断任务仍在运行，也不能把重新调用 Agent 作为所有故障的恢复方式。

每轮调度遵循“先协调已有任务，再派发新任务”：先应用本地取消和期限，协调容器、到期重试及 Outbox，再按轮询周期刷新远端状态，最后判断可领取任务和空闲槽位。远端查询失败不等于 Issue 已删除；暂停依赖该查询的新派发和发布，已有执行仍受本地期限约束。配置校验失败不能阻止取消与资源清理。

SQLite 是唯一持久化事实源，内存中的 running、claimed、retry 索引由账本派生。异步回调和重试计时器必须携带 Task ID、修订号与 Run ID，并与当前活跃 Run 比较；旧 Run 的迟到结果不能改变新 Run 的状态。`blocked`、取消及预算跨重启保留，恢复后不得仅凭 Issue 仍开放就解除阻塞。
### 11. 验证必须独立于 Agent

项目接入时登记依赖准备、测试、Lint、类型检查和构建中的适用命令。每一项标明必需或不适用，并至少存在一项与任务类别对应的有效检查；不能把“没有配置测试”显示为“测试通过”。文档项目可以配置文档校验，不强制执行不存在的编译步骤。

配置由操作者批准，保存在 worker 无写权限的位置。仓库内的配方只能从批准的基线读取并固化摘要，Issue、生成代码和 Agent 输出不能改变它。新增依赖或修改检查入口属于需要重新批准配置的任务范围。

执行前先检查基线，同一基线 SHA 和配置摘要可以复用已确认结果。原有测试不通过时报告 `blocked:baseline_failed`，不让 Agent 在一个原本坏掉的环境里反复付费尝试。

Agent 退出后先终止其容器及子进程，再提取变更并固化快照。验证在新的无模型凭据容器中执行，不能复用仍可能有后台进程的编码环境。需要发布的代码内容必须与经过验证的快照一致；检查脚本造成受跟踪文件变化时，报告快照漂移并阻塞发布。

默认保护 Runner 配置、CI 工作流、检查命令入口和凭据相关路径。拒绝路径越界、`.git` 元数据注入、逃出工作区的符号链接。对源码和测试本身仍需要人工审阅；通过测试无法证明 Agent 没有削弱断言，也无法证明验收要求已全部满足。

**Git 发布与项目执行分离。** 发布器从自己管理的干净检出重建提交，只接受经过校验的文件变更和新文件；不在 worker 可修改的 Git 配置、hooks 或工具链中使用写凭据。发布期间也不执行项目安装和测试脚本。

### 12. 失败、重试与人工接续

| 情况 | 首版处理 |
| --- | --- |
| 需求不完整、出现必须回答的问题 | 立即 `blocked:needs_input`；整理问题，释放执行资源。 |
| 模型登录失效、401/权限不足 | `blocked:auth_required`；不盲目消耗修复次数。 |
| 模型限流、网络临时失败 | 按退避等待，重启执行调用时计入总调用上限；不让多个重试层无限叠加。 |
| 项目检查不通过 | 提供固定命令的失败摘要进行有限修复；达到上限后 `failed:verification`。 |
| 触及保护路径、修改超范围 | `blocked:policy_violation`；保留变更，等待人工决定。 |
| 目标分支变化、PR 被人工接管 | 不自动覆盖；提示基线或远端结果变化，要求明确的修订操作。 |
| PR 发布失败 | 保存已验证产物，恢复 Outbox 发布；不重新调用编码 Agent。 |
| 机器或 Docker 不可用 | 暂停领取；环境恢复后先协调遗留任务，不能自动退回宿主机无隔离执行。 |
| 用户取消、Issue 关闭或 hold | 设置持久化取消标记，停止容器；发布前再次检查取消状态。 |

阻塞报告需要说明“卡在哪一步、已经完成什么、保留了什么、需要用户做什么”。不能只显示“Agent failed”。

`retry` 表示在相同输入、相同代码基线下再尝试，保留累计消耗；`revise` 表示操作者授权新的任务修订，可以使用更新后的需求和基线。首版不实现任意对话中途注入。P3 的 PR 反馈修订需绑定指定 PR 和最新 head SHA，发布前确认人工没有另行推送。

取消与远端请求存在竞争窗口：取消发生在 PR 创建请求已经发出之后时，可能仍然产生 PR。Runner 应回读并标记“任务已取消，PR 可能已创建”，停止后续写入，保留链接供人处理；不能承诺撤回已经被远端接受的请求。

### 13. 资源与费用边界

以下为首轮产品默认值，可由操作者在项目配置中调整，不是对闲置 MacBook 规格或任务性能的测量结论。

| 配置 | 初始建议 |
| --- | --- |
| 同时执行 | 全局 1 个任务；编码和验证不并行运行。 |
| Issue 轮询 | 60 秒；支持分页、限流退避，避免只读取第一页。 |
| Runner 心跳 | 10 秒；超过 90 秒未更新视为需要协调，不直接视为可以启动第二个 worker。 |
| Agent 事件静默 | 默认 5 分钟无属于当前 Run 的有效协议事件时按 stalled 处理；可按项目调整，Runner 心跳不能代替 Agent 事件。 |
| 任务执行期限 | 从首次启动计 60 分钟，修复与重启不重置截止时刻；不含入队等待。 |
| 编码调用上限 | 每个任务修订最多 3 次：首轮加最多 2 次修复或重新启动。 |
| 准备及验证 | 依赖准备最多 10 分钟；每条检查最多 10 分钟，同时受任务总期限约束。 |
| 容器资源 | 先设 2 vCPU、4 GiB 内存和 256 个进程上限，再依据首个项目峰值调整。 |
| 本机取消 | 先请求停止，10 秒后必要时强制终止；健康运行环境下，30 秒内确认容器退出或报告终止失败。 |
| 磁盘余量 | 可用空间低于 20 GiB，或使用率超过 80%，停止领取；先清理已到期产物。 |
| 出站 HTTP 重试 | 每轮最多 3 次请求，优先遵守服务端退避指示；未完成操作仍持久化等待后续协调。 |

60 分钟执行期限覆盖准备、编码与验证。已验证产物的发布恢复使用独立期限：自首次发布尝试起最多自动协调 24 小时，不启动模型；仍未成功则进入 `blocked:publish_delayed`，保留产物供显式重试。取消标记同时约束执行和发布，不能利用发布恢复绕过取消。

总期限与事件静默分别计时。Symphony 当前参考实现的 `turn_timeout_ms` 在收到流事件后重新开始等待，它不是 turn 的绝对运行上限；`max_turns` 也不能替代跨 Run 的任务累计预算。本方案的 60 分钟截止时刻和最多 3 次编码 turn 不因事件输出、正常续跑、重试或重启而刷新。[^symphony-implementation][^symphony-code]
主机断电或操作系统挂起时，Runner 无法实时执行终止动作；恢复后首先检查截止时刻。对这种停机窗口不能宣传严格的实时终止保证。

预算分为两个层次：执行时间、调用次数和容器资源由 Runner 控制；美元费用基于 CLI 回传或配置价格估算。金额阈值只能在有足够用量信息时触发停止，存在上报延迟，不能承诺绝对不超支。

费用记录包含原始用量、金额、币种、来源与 `reported / estimated / unknown` 类型。没有返回金额时不填 0；“CLI 报告的成本”也不等于供应商最终账单。Claude 官方特别说明其成本数据是客户端估算，续接会话还可能包含前次运行的累计费用。[^claude]

所有重试成本都计入任务修订累计。若适配器返回会话累计值，应记录前后差额和会话归属，避免把累计费用重复相加。不能通过创建新的 Run 绕过任务预算。

衡量经济性使用：**每个被采用成果的成本 =（全部任务模型费用 + 分摊机器费用 + 接入、维护和人工审阅成本）÷ 实际被采用的成果数。** 分母为 0 时展示原始投入，不生成没有意义的单价。

### 14. 凭据、信任与数据去向

| 资源 | 放置与访问约束 |
| --- | --- |
| GitHub 凭据 | 初版使用只选定目标仓库的细粒度凭据；按实际 API 配置 Contents、Issues、Pull requests 所需权限，保存在宿主控制侧。worker 不获取 GitHub 写凭据。[^github-permissions] |
| 模型凭据 | 使用专门供此用途、可撤销的凭据，只提供给编码执行环境，不传入验证环境。采用官方支持的鉴权方式。 |
| Runner 状态与控制配置 | 专用用户管理，不挂载进 worker，不允许 Issue 修改镜像、shell 启动参数或凭据引用。 |
| 生产数据与凭据 | 不登记、不挂载，不作为测试夹具；仅使用独立测试数据。 |
| 代码与日志 | 工作副本和完整日志主要保存在自有机器；代码托管交互和模型请求会按工作流发送相应内容，不能宣传为“数据完全不出本机”。 |

**首版仅面向可信的自有项目，不能宣称是运行任意恶意代码的托管沙箱。** 模型 CLI 与项目代码同处编码容器时，任务代码可能读取该容器的模型凭据；仅把凭据放在环境变量里并不构成秘密隔离。官方 Codex 自动化文档也提醒不要把 API key 暴露给运行不可信项目代码的同一环境。[^codex]

因此首版不处理陌生人的公开任务，也不共享日常高权限账户。面向公开任务或多租户之前，必须增加宿主侧模型凭据代理、限定请求能力、可验证的网络出口控制和更强执行隔离，并单独进行安全验收。未完成这些工作不扩大信任范围。

首版不承诺域名级网络白名单，容器隔离也不等于阻断所有网络访问。需要生产内网隔离的使用场景，应在独立网络和主机中部署并另行验证。

模型服务账号、GitHub 凭据、目标仓库是必需外部依赖；Docker 运行环境与 worker 镜像是执行依赖。镜像仓库凭据仅在使用私有镜像时需要。Tailscale 是可选运维入口，首版轮询不依赖公网入站端口。当前没有需要接入的 MCP 服务器或 SaaS 控制平面。

### 15. MacBook 部署与可用性

沿用闲置 MacBook，先登记 CPU 架构、系统版本、内存、可用空间以及 Docker 实际可用状态，再确定 worker 镜像架构。原讨论的 16 GB 内存和 100 GB 可用空间可以作为试运行预算参考，不作为已经确认的硬件事实，也不据此建议立即购买新机器。

首版使用专用 macOS 用户、登录后的 LaunchAgent 和已启动的 Docker Linux 环境。Apple 文档说明用户级 LaunchAgent 随用户登录加载；Docker Desktop 的对应启动选项也是登录时启动。[^launchd][^docker-settings]

**可用性承诺：在系统已解锁、用户执行环境及 Docker 就绪后自动运行和恢复。** 不能把这一点扩写成“任何断电重启后都能无人处理地恢复”。开启 FileVault 时自动登录不可用，不能建议通过关闭磁盘加密来兑现错误承诺。[^filevault]

部署检查应分别覆盖 Runner 崩溃、Docker 重启、系统重启和睡眠唤醒。接电与睡眠策略由设备拥有者配置并实测，不提供一条命令便保证合盖长期运行的承诺。主机自检不能检测自己的持续断电；需要离线告警时，由独立监测端检查心跳，列入后续运营能力。

若这一可用性边界不能满足实际使用，再迁移到 Linux 单机 Runner 和容器 worker，沿用相同任务契约。先迁移整套单机服务，不立即拆成“VPS 控制端 + MacBook 执行端”。

### 16. 配置、运维入口与产物留存

以下是拟定的 CLI 接口，不是本轮已安装的命令。涉及任务的参数均使用持久化 Task ID。

| 命令入口 | 行为 |
| --- | --- |
| `runner project add` | 登记仓库、基线分支、执行镜像、允许操作者与凭据引用，导入并批准基线 WORKFLOW.md 的检查配方和内容摘要。 |
| `runner project sync` | 操作者显式导入指定提交的 WORKFLOW.md；校验通过后采用新配置摘要，仅作用于后续授权的任务修订。 |
| `runner doctor` | 检查系统、Docker、镜像架构、目录权限、仓库和模型连通性；输出具体可修复问题。付费模型探测需显式选择。 |
| `runner enqueue` | 从任务文件或指定 Issue 生成任务快照并入队；返回 Task ID。 |
| `runner serve` | 前台运行同一个调度内核；由 launchd 管理时也调用此入口。 |
| `runner status` / `runner tasks show` | 展示主机状态、排队情况或单个任务的阶段、产物和下一步。 |
| `runner tasks cancel` / `retry` / `revise` | 分别取消、按原修订再试、授权生成新修订；记录操作者和原因。 |
| `runner pause` / `resume` | 暂停或恢复领取；暂停不等同于取消已经开始的任务。 |
| `runner gc --dry-run` / `runner gc` | 预览或清理到期资源，仅处理本产品拥有标记的对象。 |
| `runner export` | 导出指定任务的快照、检查结果及脱敏日志，用于接管和排障。 |

配置分为两份：宿主 TOML 保存 `schema_version`、仓库登记、操作者、镜像、权限、资源硬上限、留存、凭据引用和已批准的 workflow 提交/摘要；仓库根目录 `WORKFLOW.md` 保存项目工作配方与 Agent 提示正文。前者由操作者控制，后者便于随项目审阅和版本管理。

WORKFLOW.md 采用 YAML front matter 加 Markdown 正文，但使用 Agent Runner 自己的版本化 schema；不承诺可以直接运行 Symphony 配置。首版 front matter 只接受 `schema_version`、`prepare`、`checks`，命令使用参数数组，每项检查声明名称、必需性与超时；非适用项单独说明原因。Markdown 正文作为项目提示，任务快照由 Runner 独立附加，不支持任意模板执行或环境变量展开。未知字段、无效命令和越过宿主上限的配置导入失败；仓库不得覆盖凭据或权限。

接入时必须生成并批准项目配方。每次任务固定代码基线、workflow 内容摘要及有效配置摘要，worker 中对 WORKFLOW.md 的修改不能影响当前或后续运行。配置更新走显式 `project sync`；导入失败不替换上一批准版本，提示新版本未采用。已运行任务维持原快照，新的授权任务使用明确显示的批准版本；首版不引入自动热加载。代码基线中的 workflow 与批准摘要不同则阻塞该次入队，要求先同步或选择匹配基线。

SQLite 使用版本化迁移；运行日志使用 JSONL，统一记录 Task ID、Run ID、thread/turn ID、阶段、事件时间和错误类型。状态输出区分 Runner 心跳、Agent 最后事件、最后完成的检查以及“等待模型、工具执行中、等待验证、等待发布、需人工处理”。协议没有提供某项细节时显示未知，不从持续输出推断任务正在有效推进。内部时间使用 UTC，展示时按用户设置转换。

代码按配置与 CLI、任务账本与调度、GitHub 集成、工作区与容器、Agent 适配器、验证、发布和报告分模块。它们共享明确的数据契约，不拆成多个网络服务。需要另加的实现文件包括项目打包配置、worker 镜像定义、launchd 配置和契约/故障测试。

留存建议：成功任务的执行目录保留 24 小时，失败或阻塞目录保留 7 天；删除前必须已有导出的变更产物与检查记录，导出变更包默认保留 90 天。没有可恢复副本的唯一未提交变更不自动删除。过期产物在任务中保留“已过期”的标识，不伪装成仍可下载。

脱敏原始日志默认保留 7 天，单 Run 上限 100 MiB、总日志上限 2 GiB；达到上限保留状态和必要错误摘要，注明日志截断。任务元数据与证据摘要保留 90 天。支持操作者显式延长单个任务留存；禁止按通用目录名或全局 Docker prune 清理其他项目。

### 17. 验收矩阵

验收必须同时覆盖正常交付、故障恢复和拒绝执行。使用可控的假 Agent 和模拟 GitHub 故障测试调度语义，再在专门的测试仓库执行真实端到端烟雾测试；真实模型调用与仓库写入属于实施阶段的明确测试活动。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 有复现与验收条件的小缺陷 | 产生单个 Draft PR，代码 SHA、任务和各检查结果可关联。 |
| A02 | 基线测试已失败或缺少有效检查 | 在编码前阻塞，说明基线问题；不能报告绿色结果。 |
| A03 | 轮询重复、CLI 与轮询同时提交同一修订 | 只有一个 Task 和一个活跃执行；无重复 PR。 |
| A04 | Agent 未通过验证但声称任务完成 | 状态以独立检查为准；触发有限修复或失败。 |
| A05 | 验证完成后快照改变 | 阻塞发布，无法用旧测试结果给新代码背书。 |
| A06 | Agent 静默，或持续输出但超过总期限 | 分别命中事件静默和绝对期限；在主机健康时终止整个容器，累计调用数与截止时刻不被重置。 |
| A07 | 本机取消、Issue hold 或关闭 | 在相应检测窗口内停止；不发起新的发布。已有在途请求完成后记录实际远端状态。 |
| A08 | Runner 在编码中被强制停止 | 重启先终止/协调遗留容器，从持久化快照接续；不能并行重跑同一任务。 |
| A09 | 推送成功或创建 PR 成功，但响应丢失 | 回读已有远端结果，找回同一分支与 PR；不重复编码和创建。 |
| A10 | GitHub 断网、限流或 5xx | 保留结果并退避；恢复后只做未完成的发布或状态同步。 |
| A11 | 凭据过期或模型不可访问 | 报告明确鉴权/连接问题；不无限循环，不打印凭据。 |
| A12 | 非授权 Issue、正文要求越权、改保护文件 | 拒绝领取或阻塞发布；正文不能提升权限或改执行配方。 |
| A13 | 路径越界、恶意符号链接、篡改 Git hooks | 变更提取/发布拒绝危险内容；不能让写凭据进入项目脚本。 |
| A14 | 同一费用累计值重复回传、费用缺失 | 不重复累计；缺失显示未知；修订累计额度不随 Run 重置。 |
| A15 | 磁盘不足、日志超限、清理运行 | 停止领取并可诊断；保留唯一变更，不影响其他项目资源。 |
| A16 | Docker 重启、睡眠唤醒、系统冷启动 | 分别验证恢复前置条件；未登录或 Docker 未就绪时不虚报健康。 |
| A17 | Issue 正文在执行中更改、人工推送任务分支 | 检出输入或远端漂移，阻塞有歧义的发布，不覆盖人工工作。 |
| A18 | 无代码变更，或 PR 被关闭但未合并 | 记录 `no_change` 或 `closed_unmerged`，不计为成功采用。 |
| A19 | WORKFLOW.md 被任务修改、无效更新或基线与批准摘要不符 | 不能改变固定配方或宿主权限；无效更新不被采用，配置漂移阻塞入队。 |
| A20 | turn 正常结束或 Draft PR 已生成，但 Issue 仍 open | turn 结束进入验证；review_ready 不自动编码，无一秒续跑或预算重置。 |
| A21 | 输入或审批需求导致 blocked，随后 Runner 重启 | 阻塞原因仍存在且不派发；只有明确操作才能接续，不自动回答审批。 |
| A22 | 取消或修复开始后，旧 Run 事件及重试定时器迟到 | 拒绝不匹配 Run ID 的状态更新；取消响应必须与真正停止区分。 |
| A23 | 入队后 ready 替换成 running；随后加 hold | 展示标签变化不取消，hold 按检测窗口停止；远端读取失败不被误判为已关闭。 |

实现仓库的基础测试入口定为 `python -m unittest discover -s tests -v`，覆盖状态转换、事件解析、预算、授权和发布故障。容器隔离、主机恢复以及实际 GitHub 权限必须另做环境验收，不能以模拟测试通过替代。

P1 至少覆盖 A01—A06、A08—A14、A19—A22 中不依赖 Issue 轮询的部分，以及资源清理；P2 覆盖全表。20 个真实任务评估必须在这些确定性检查通过后进行，避免拿模型结果掩盖调度器缺陷。

### 18. 实施、升级与退出路径

第一项实施交付是 P1 的可安装 CLI：接入一个测试仓库，完成单任务容器执行、独立验证和 Draft PR 发布，并具备取消和中断恢复。不是先开发看板或三个 Agent 适配器。

P1 同时交付 WORKFLOW.md 导入及固定快照、App Server 单 turn 适配器、本地恢复协调和取消/预算契约；P2 将协调循环扩展至 Issue 状态、自动领取及状态呈现。Symphony 参考实现只作代码与语义参考，不成为另一个与 Runner 同时争抢任务的常驻服务。
发布物应包括固定依赖的 Python 包、与其对应的 worker 镜像摘要、配置格式版本、版本变更记录以及可运行的验收命令。CLI 和镜像一同经过兼容测试；生产使用固定版本，避免无人值守期间自动跟随 Agent CLI 最新版本。

升级流程为：暂停领取、结束或停止当前执行、用 SQLite 备份接口获取一致性备份、备份配置与产物索引、应用迁移、运行诊断及单任务烟雾测试，再恢复领取。不能只复制正在使用中的数据库主文件而忽略一致性要求。[^sqlite-backup]

回滚优先恢复兼容旧配置的程序和镜像。数据库发生不兼容迁移时从升级前备份恢复，并保持暂停，先与已产生的远端分支、PR 和 Outbox 操作协调后再继续；直接恢复旧数据库然后立即重跑可能造成重复外部效果。

卸载首先停止领取与执行，导出任务和变更，撤销专用凭据，再删除明确选择的本地产物。用户仓库、远端 PR 和手工创建的分支不随卸载自动删除。

### 19. 分发、商业验证与维护负担

当前阶段定位为自用验证和小范围邀请试用，尚不承诺开源协议或 SaaS 商业模式。产品名称 Agent Runner 暂为工作名称；公开发布前再检查命名和分发条件。

推荐的商业实验是**个人自托管年度更新维护版**，试探价可设为 199 元/年。这只是访谈和报价实验的起点，不是市场价格结论，也不是立即收费决定。模型、机器费用由用户自己承担；不提供共享模型账号、无限运行额度或无限环境定制支持。

先邀请 5 位已经使用编码 CLI 的开发者接入真实仓库，记录首个成功交付所需人工帮助、持续使用、失败接管时间和维护成本。至少 3 人持续使用、至少 2 人对明确交付范围作出付费承诺，再决定是否建设收费与许可功能；样本过小，不能据此推算市场规模。

首个分发内容是可复现的真实任务案例：输入 Issue、执行过程、验证证据和最终 PR，同时展示一个失败后如何接管的例子。优先面向实际使用编码 CLI 的开发者社群和项目文档分发，不以“全自动替代程序员”宣传。

可收费前要完成安装、首次接入、升级回滚、试用/许可边界、数据去向说明、故障支持范围和退款触发条件。首版只有在作者机器上跑通，不足以支持收费。

最容易被低估的长期负担是 CLI 输出和鉴权变化、项目依赖环境差异、GitHub 权限与发布异常，以及用户电脑的电源和运行状态。每个新增适配器都要承担版本兼容与契约测试成本；没有真实任务需求就不接入。

**停止或转向条件**：20 个自用任务后，维护加审阅时间没有下降；现成方案满足同样要求且更易维护；试用者只想要一次性配置而不持续使用；或每位用户支持成本已经超过其愿付价格。出现这些情况时，应收敛为自用脚本、现有平台适配或安装服务。

### 20. 最脆弱的假设与决策责任

| 假设或尚未现场验证的事实 | 影响 | 验证责任与处理规则 |
| --- | --- | --- |
| 目标任务能写出有效验收条件 | 否则无法定义可信交付，成功率没有意义。 | 产品负责人预登记 20 个任务；缺条件的任务在入队前补齐。 |
| 闲置 MacBook 能提供可接受的在线窗口 | 否则无人值守交付被电源、睡眠和登录状态打断。 | 部署者在设备上运行 doctor 与 A16；不满足时采用 Linux 单机部署，不扩大云端架构。 |
| 首个 Agent 的鉴权与事件接口适用于固定 worker | 否则无法稳定自动执行与记录成本。 | 实施者在 P1 固定版本做真实烟雾测试；不把个人订阅状态等同于自动化授权。 |
| 用户为减少接管而非“多 CLI 按钮”付费 | 否则独立产品缺少可持续价值。 | 产品负责人完成外部试用和报价实验；达不到门槛不建设收费系统。 |

这些事项不会阻止产出本规划，但会阻止越过相应的发布门槛。本轮没有访问目标闲置 MacBook 的配置，也没有验证其模型账号、GitHub 权限或项目检查命令，不能将公开文档核对当成现场部署验证。

### 21. Symphony 借鉴决策

**采用方向：把 Symphony 作为编排设计参考，把 Agent Runner 的产品承诺落在可验证、可恢复的任务交付。** OpenAI 将 Symphony 定位为规范与参考实现，并明确不计划把它维护成独立产品；借鉴不等于把其演示效果、维护承诺或默认值直接变成我们的承诺。[^symphony-position]

本次核对了 README、SPEC.md、Elixir 使用说明及实际源码；代码基线为 `be10a1b79df723d6d7612b5651c8522704dafb2e`，提交日期为 2026-09-15 UTC，核对日期为 2026-09-22。当前已有 GitHub Issues 适配器与 macOS 发布构建目标，不能将“支持 GitHub / Mac”当作独占能力；发布构建目标也不代表已验证用户这台 MacBook 的安装体验。[^symphony-implementation][^symphony-code]

| 借鉴点 | 本项目采用的具体方式 | 所在章节 |
| --- | --- | --- |
| 工作流与项目一起版本管理 | WORKFLOW.md 保存配方和项目提示，任务固定批准摘要；宿主保留凭据与资源控制。 | 第 16 节 |
| 先协调、后派发 | 同时处理取消、过期、旧容器、远端状态与发布恢复，再派发；所有状态由 SQLite 统一落账。 | 第 10 节 |
| 显式 Agent 会话协议 | 用 App Server 的 thread、turn、事件、审批需求与中断信号管理单次执行。 | 第 9 节 |
| 保留工作成果与生命周期 | 同一任务修订可保留变更并有限修复；每次执行仍使用临时容器，清理前保留证据。 | 第 8、16 节 |
| 失败分类与运行可观测性 | 区分静默、超时、输入缺失、验证失败和发布失败，展示准确阶段与会话归属。 | 第 12、13、16 节 |

参考实现中，`orchestrator.ex` 的 `maybe_dispatch` 先协调运行与阻塞项，再选择候选任务；`agent_runner.ex` 将正常 turn 结束与 Issue 完成分开；`workflow_store.ex` 在重新加载失败时保留上一有效配置；`codex/app_server.ex` 处理会话、流事件和输入请求。这些是本次实际阅读后提取的机制，具体产品策略按上表重新约束。[^symphony-code]

**明确保留的差异**：本项目持久化阻塞和预算，不采用仅靠内存及 tracker 重建全部执行记录；验证、提交与 PR 写操作由 Runner 负责，不仅依靠 Agent 遵守提示；审核态停止编码；配置不在任务执行中热更新；工作区隔离叠加 Docker，并不把目录边界当成完整沙箱。参考实现支持宿主代理 tracker 工具调用，但“Agent 看不到 token”不等于“Agent 只能调用允许的操作”；首版不向 Agent 暴露通用 GitHub 写接口。[^symphony][^symphony-implementation]

暂不引入 Elixir/OTP、Phoenix 看板、全部 tracker 适配器、远程多 worker 或自动合并。保持 Python 与单机范围，是当前产品维护成本的选择，并非认为这些现成能力不可用。直接配置 Symphony 仍是第 3 节的最小替代方案；比较时使用相同仓库、任务、模型配置和交付门槛，登记配置工时、接管次数、人工审阅投入和总费用，不把“能自动开 PR”本身当作优势。

新增 A19—A23，并强化 A06，验证本次借鉴带来的配置、终态、阻塞、迟到事件与标签语义。当前只更新规划；未安装或运行 Symphony，未实现 App Server 适配器，也未启动实际 Agent 或写入远端 Issue/PR。

[^sqlite-backup]: SQLite：[Online Backup API](https://www.sqlite.org/backup.html)。用于一致性备份方案；实施时需验证所用 Python SQLite 接口行为。
